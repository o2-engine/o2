# Пайплайны

AI-пайплайны контента: графы нод, которые превращают текст, картинки и звуки в ассеты через API провайдеров и локальную обработку. Исходники - в `o2/Editor/Sources/o2Editor/Pipeline` (пространство имён `Editor`); редакторская часть - окно Pipeline. В рантайме остаётся только `o2::PipelineAsset` - ассет `.pipeline`, хранящий граф как `DataDocument`; `PipelineGraph::LoadFromAsset` / `SaveToAsset` переводят документ в граф редактора и обратно. Документ - JSON пайплайна AssetsLine (см. Формат).

> **Три реализации - менять вместе.** Редактор пайплайнов существует в трёх экземплярах: веб-редактор и сервер AssetsLine (`AssetsLine/`: `shared/`, `backend/src/`, `frontend/src/nodeEditor/`), этот редактор o2 (`o2/Editor/Sources/o2Editor/Pipeline/` и `o2/Editor/Sources/o2Editor/Windows/PipelineWindow/`) и плагин Unity (`AssetsLineUnity/Packages/com.assetsline.pipelines/`). Все три читают и пишут один и тот же документ `.pipeline` и синхронизируют пайплайны друг с другом. Изменение поведения пайплайна, типа ноды, ключа конфига, формата файла, правил исполнителя и кеширования или интерфейса нод нужно вносить во все три сразу, обновляя их тесты и документацию, - иначе синхронизированные пайплайны разойдутся.

## Внешний вид окна

`Windows/PipelineWindow/PipelineTheme.*` хранит две палитры (тёмная - токены AssetsLine, светлая - цвета редактора o2) под именами CSS-токенов, общими с AssetsLine и Unity, текущую тему (`ViewPrefs.json`, ключ `theme`) и версию, которую опрашивает редактор: при смене `PipelineEditor::ApplyTheme` перестраивает карточки и перекрашивает меню. `PipelineDraw` рисует сглаженные скруглённые заливки, обводки с градиентом и почти гауссовы тени (кольца на ±2σ) с каймой в один пиксель цели; шахматка (подложки картинок, сцена композера) - одна текстурированная скруглённая сетка с повторяющейся плиткой 2 × 2 текселя, а точки холста, пока они чаще 32 пикселей, - один квад с плиткой из десяти на десять клеток, пересобираемой при смене зума: квадами при отдалении их были сотни тысяч на кадр. Контролы (`PipelineThemeControls.cpp`: поля, кнопки, переключатели, сегменты, списки, меню) собраны из этих примитивов, а не из спрайтовых стилей редактора; `PipelineRichText` раскладывает текстовые результаты в Markdown (абзацы через 0.5 em, `**жирное**` полужирным начертанием). Метрики карточек и тел следуют константам AssetsLine (`frontend/src/nodeEditor/constants.ts`, `nodeRenderers.tsx`: GAP 7, поле 14 + 16.1·строк, кнопки 27.52, свёрнутый список 31.84, строки fx через 6). Закрытый переменными окружения UI-тест `PipelineThemeGallery` снимает каждую карточку бандла AssetsLine там же, где она стоит в веб-эталоне, с дампом блоков (`PipelineLayoutDump`) для попиксельного и поблочного сравнения.

## Граф

- **Editor::PipelineGraph** — `nodes`, `edges`, сохранённая камера. `Validate()` сообщает о несовпадении типов и циклах, `WouldMakeCycle(from, to)`, `FindEdgeToPort`, `GetOutgoingEdges`, `RemoveDanglingEdges`, `ResolveSeeds()` (ноды картинок наследуют seed ноды-картинки выше по графу при `inheritSeed`), `ComputeSignatures()` — хеш содержимого каждой ноды из её конфига (без UI-ключей, см. `GetUiOnlyConfigKeys()`), сигнатур нод выше по графу и seed.
- **Editor::PipelineNode** — `id`, `nodeType`, `position`/`size` (ось y вниз, как в веб-редакторе), `inputs`/`outputs` (`Editor::PipelinePort`: `id`, `name`, `portType`, `custom`), `config` — `DataDocument` с `GetConfigString/Number/Bool/Value`, `SetConfig*`, `RemoveConfig`, `HasConfig`. Добавленные пользователем входы хранятся в `customInputs` (`GetCustomInputs/SetCustomInputs`); `PipelineNodeRegistry::SyncNodeWithSchema` пересобирает список портов из схемы и пользовательских входов.
- **Editor::PipelinePortType** — `Text`, `Image`, `Video`, `Audio`; связь соединяет только порты одного типа.
- **o2::PipelineAsset** (движок) — ассет `.pipeline` с документом графа; редактор читает его в `PipelineGraph` и записывает обратно при каждом изменении.

## Формат
Файл `.pipeline` - это документ `Pipeline` AssetsLine: `schemaVersion`, `id`, `name`, `nodes` (`id`, `type`, `position`, `size` как `{width, height}`, `config`, `inputs`/`outputs` из `{id, name, type, color?, custom?}`), `edges` (`id`, концы, `points`), `camera` (`{x, y, scale}`: экран = мир * scale + (x, y)). `PipelineGraph::LoadFromJson` / `SaveToJson` (и `LoadFromJsonString` / `ToJsonString`, их же используют отмена и буфер обмена) читают и пишут его; поля, которые редактор не использует - `annotations`, `icon`, `color` порта, всё более новое - хранятся в `extra` графа, ноды и связи и пишутся обратно без изменений. Целые числа пишутся целыми, остальные округляются до 1/1000, поэтому документ, прочитанный и записанный без правки, не меняется побайтно. Камера пересчитывается через фиксированный номинальный вид (`GetNominalViewSize`). Старый формат o2 (`{"graph": ...}`, рефлексия) распознаётся `IsLegacyDocument`, читается и при следующем сохранении пишется в новом формате.

Числа, которые оба редактора выводят из документа, совпадают: неявный seed - как в AssetsLine (32-битный FNV-1a от id ноды, семантика `Number()` для `config.seed`, наследование выключено только буквальным `false`), список UI-ключей конфига одинаков. Финишная нода без `assetPath` пишет в `Generated/<filename>` (`PipelineNodeRegistry::GetFinishAssetPath`). Вставка даёт нодам и портам новые id и переназначает id, на которые ссылается конфиг (`PipelineNode::RemapConfigPortIds`: пользовательские входы, слои composer, регионы extract).

## Типы нод

`Editor::PipelineNodeRegistry` хранит все `Editor::PipelineNodeSchema` (`type`, `label`, `category`, `description`, `inputs`, `outputs`, `addableInputs`, `instant`, `perPortRun`, `dynamicOutputs`, `defaultSize`) вместе с реализацией (`Editor::PipelineNodeBase::Run` — `Coroutine<PipelineRunResult>`, получающая контекст выполнения и значения входов). `AllSchemas()`, `GetSchema(type)`, `CreateNode(type, position)`, `IsFinishType`. Кроме `Run` реализация может переопределить `InitNode(node)` (конфиг, с которым создаётся нода), а для ноды с `perPortRun` - `SyncPorts(node)` (она сама владеет списком выходов, и `SyncNodeWithSchema` не трогает выходы схемы), `PortCacheExcludedKeys()` и `PortCacheVariant(node, portId)` - ключи конфига, которые выбрасываются из попортовой сигнатуры, и то, что добавляется в неё для конкретного порта.

`Editor::PipelineRegions` - список частей ноды вырезания: `PipelineExtractRegion` (`id` - id выходного порта с этой частью, `name` - что вырезать и имя порта, нормализованная рамка, `ownTransparency` - есть ли у неё собственные настройки фона), `Read`/`Write` по конфигу ноды (нода, сохранённая до появления частей, читается как одна часть из `prompt` и `roi`; `Write` оставляет члены части помимо id, имени и рамки - её собственный `transparency`, всё более новое - у части с тем же id), `PortNames` (уникальные, непустые), `SyncPorts` (пересобирает выходы, сохраняя id, поэтому связи переживают переименование; у ноды без списка частей остаётся ровно один выход с именем `out` - её первый порт со связями, остальные удаляются, - потому что AssetsLine ищет этот выход по имени из схемы и добавлял фантомный `out` рядом с портом, названным по промпту), `RegionOfPort`, `FindTransparency(node, portId)` (собственные настройки фона части, null, если она следует ноде), `SetOwnTransparency(node, portId, own)` (даёт части полную копию её действующих настроек или убирает её), `autoSplitPrompt` и `ParseAutoSplit(answer)` (модель отвечает `box_2d` в виде `[ymin, xmin, ymax, xmax]` на сетке 0..1000; найденные так части начинают без собственных настроек). Вставка переназначает id частей на месте, поэтому часть сохраняет настройки при копировании.

**Фон по частям.** Часть может нести `transparency` - шесть ключей `transparentBg`, `transparentMode`, `chromaColor`, `chromaTolerance`, `chromaSoftness`, `chromaSpill` (`PipelineTransparency::SettingKeys()`), записанных целиком в момент перевода части на собственные настройки. Если объект есть, он заменяет эти ключи ноды для этой части; ключ, которого нет в неполном объекте, берётся у ноды, затем по умолчанию (`false`, `twoPass`, `#00b140`, 30 / 15 / 60). Всё, что читает их для запуска, идёт через действующие настройки части: `PipelineTransparency::SettingValue(node, portId, key)`, `Read(node, portId)` (промпт вырезания, два прохода или хромакей), `UsesChromaPostStep(node, portId)`, `ApplyChromaPostStep(node, raw, portId)`, `AnyChromaPostStep(node)` (автоприменение ползунков вырезания в редакторе), `ImageGenerations(node)` (число генераций одного запуска: на часть две для прозрачного рендера в два прохода, иначе одна - это число AssetsLine умножает в цену на кнопке запуска; редактор o2 цену не показывает) и сырые рендеры в синхронизации.

**Фон, который делает модель.** `PipelineTransparency::SupportsNativeTransparency(model)` отвечает по id без пробелов по краям и начального `models/`, в любом регистре: да для `gpt-image…` (OpenAI), для `openai/gpt-image-…`, кроме `openai/gpt-image-2` и его датированных снимков `openai/gpt-image-2-YYYY-MM-DD`, для `openai/gpt-5-image`, `openai/gpt-5-image-mini` и `sourceful/riverflow-v2.5-pro`; нет для всего остального. Режим решает id, сохранённый в ноде; вызов с прозрачным фоном берёт затем только маршруты, чей собственный id его рисует (`RoutesFor(model, true)`), и если ни для одного нет ключа, родной провайдер сообщает об отсутствии своего. Для них `Read` даёт действующий `mode` `native`, что бы ни было в `transparentMode`, а способ из конфига хранит в `storedMode`; конфиг не переписывается, поэтому `WriteSettings` и часть `bg:[...]` сигнатуры порта берут `storedMode`. `UsesNativeTransparency(node, portId)` истинно, когда фон включён (для `aiRemoveBg` всегда) и режим `native`. Такая нода или часть не хромакейная: `UsesChromaPostStep` / `AnyChromaPostStep` ложны, поэтому исполнитель не хранит сырой рендер, не добавляет вариант `chroma-raw` и ничего не вырезает, ползунки вырезания не запускают автоприменение, а `ImageGenerations` считает одну генерацию. Ноды делают один вызов с `transparentBackground` в `AiRouter::GenerateImage`. `OpenAiProvider` кладёт `"background": "transparent"` в тело `images/generations` и поля `background` и `output_format` в форму `images/edits`; `OpenRouterProvider` отправляет вызов в свой images API с `background` и `output_format` в теле (`BuildImagesBody`: `model`, `prompt`, `n`, референсы в `input_references`, без seed и размера); Gemini флаг игнорирует. Промпты не называют цвет подложки (`nativeBackdrop`, `nativeEditSuffix`); `imageExtract` обрезает ответ по альфе и возвращает его необрезанным, если в нём нет ни одного видимого пикселя.

Категории: источники (`sourceText`, `sourceImage`, `sourceAudio`), преобразования (`textCompose`, `textConcat`, `drawImage`, `imageOutline`, `imageShadow`, `imageGradient`, `imageColor`, `audioProcess`), AI (`aiText`, `textEdit`, `promptGen`, `nanoBananaGen`, `imageEdit`, `imageExtract`, `removeBackground`, `aiRemoveBg`, `aiUpscale`, `videoGen`, `sfxGen`, `ttsSpeech`, `musicGen`), выходы (`composer`, `finishImage`, `finishText`, `finishVideo`, `finishAudio`). Ноды с `instant` выполняются локально и автоматически перезапускаются редактором - от результатов, которые показывают их входы (`PipelineExecutor::ExecuteSingle`): перегенерированная нода сохраняет сигнатуру, и сохранённый результат эффекта мог быть сделан из старой картинки. Запуск только из кэша всё равно считает источники - они лишь читают свой файл.

Провайдеры (`o2/Pipeline/Providers`): `GeminiProvider` (текст, генерация и правка картинок, Imagen, TTS, музыка Lyria), `OpenAiProvider` (текст через chat completions, картинки через `images/generations`, а с референсами - через multipart `images/edits`), `OpenRouterProvider` (текст и картинки на любой модели OpenRouter через chat completions API; картинки ещё и через images API `POST /images`, куда идут вызов с прозрачным фоном и модели, умеющие только картинки: вызов chat completions, получивший 404, повторяется там), `ElevenLabsProvider` (речь, звуковые эффекты), `VideoProviders` (Veo, Kling). Текстовые и картиночные ноды и `Auto split` ноды extract вызывают `AiRouter`, который выбирает провайдера и его ключ по id модели. `FamilyOf` даёт родного провайдера: начальный `models/` (длинная форма id Gemini) отбрасывается, затем id со слэшем (`vendor/model`) - OpenRouter, `gpt-…`, `o<цифра>…`, `chatgpt-…` и `dall-e…` - OpenAI, любой другой id - Gemini. `RoutesFor` перечисляет маршруты в порядке перебора: родной и иногда альтернативный с переписанным id: `gemini-X` - OpenRouter `google/gemini-X`; текстовые id OpenAI и `gpt-image-X` - OpenRouter `openai/<id>`; `google/gemini-X` и `google/gemma-X` - Gemini `gemini-X` / `gemma-X`; `openai/<id>` - OpenAI `<id>`. Альтернативы нет у `imagen-…`, `dall-e-…`, составных id `openai/…` с `-image`, кроме `openai/gpt-image-…` (`openai/gpt-5-image`), id с суффиксом варианта `:`, алиасов Gemini `-latest` и у остальных вендоров. `ChooseRoute` берёт первый маршрут, для которого задан ключ, и пишет в лог выбор не родного маршрута; если ключей нет совсем, родной провайдер сообщает об отсутствии своего ключа. Неудачный вызов на другом маршруте не повторяется. Ключи берутся из `Editor::PipelineSettings` (`Work/Pipelines/PipelineSettings.json`). Запросы идут через `o2Network.RequestAsync`, повторы сообщаются событиями `Retry`.

Помощники для картинок: `Editor::PipelineImageOps` (масштаб, `Fit` - вписать в размер с сохранением пропорций на прозрачном холсте, обрезка, обрезка по содержимому, хромакей, двухпроходная маска, обводка, тень, градиент, цветокоррекция, отражение, поворот, nine-slice, `ComposeLayers`, `Blank`, доступ `Pixel` — битмапы RGBA, `Pixel(bmp, x, y)` в координатах картинки), `Editor::PipelineTransparency` (пост-шаги белый/чёрный и хромакей), `Editor::PipelineAudio`. `ResolveComposerLayers(node)` перечисляет слои композера от нижнего к верхнему (входы-картинки, дубликаты из `dupLayers`, порядок из `layerOrder`).

## Выполнение

`Editor::PipelineExecutor::Execute(pipelineId, graph, targetNodeId, dirtyNodeIds, cachedOnly)` выполняет цепочку выше целевой ноды в порядке зависимостей. Результаты кешируются в `Work/Pipelines/cache/<pipelineId>/{content,previews,ran}` по сигнатуре ноды: нода с совпавшей сигнатурой берётся с диска, `cachedOnly` берёт ноды провайдеров из кеша или, если его нет, из последнего отрисованного превью (без отметки о запуске) и отказывает только нодам без того и другого (`Not cached`). `ResolveSourceValue(node, assetsPath, value, error)` (`Nodes/PipelineNodesCommon.h`) - единственное место, где нода-источник превращает конфиг в значение: через него работают сами источники, и им же редактор даёт источникам значение без запуска. `PipelineUtils::PrettyModelName(id)` переводит id моделей в названия для списков моделей; `PipelineModelMenu` (`Pipeline/PipelineModelMenu.h`) держит правила меню моделей, общие с `shared/modelMenu.ts` AssetsLine (группа id, порядок и сворачивание групп, поиск по полям, Recent, строка своего id), а `PipelineModelPicker` (окно Pipeline) рисует его всплывающим окном `PipelineEditor`; `PipelineOptionPicker` - такое же окно без поиска для фиксированного выбора с иконками и подсказками (цель генератора промптов). `PipelineGraph::GetRunTargets()` возвращает цели запуска всего графа: все ноды без исходящих связей, финишные первыми, без источников, которые никто не читает. Нода с `perPortRun` считается выход за выходом: производятся только порты, которые читает ветка (целевая нода считает все свои), каждый со своей сигнатурой (общий конфиг без `PortCacheExcludedKeys` плюс `PortCacheVariant`) и своим превью (`GetPortPreviewPath`, `LoadPortPreview`, событие `NodeOutput` с `portId`), поэтому упавшая или изменённая часть не трогает остальные; потребитель такого выхода хешируется по той части, которую читает (`PipelineGraph::ComputePortSignature`, `OutputSigKey`), так что две одинаково настроенные ноды на двух частях не делят ячейку кеша. Часть сигнатуры порта, отвечающую за прозрачность, даёт `PipelineTransparency::PortCacheSuffix`: часть без собственных настроек хешируется байт в байт как до их появления (при хромакее ноды её сырой рендер выбрасывает `chromaTolerance/Softness/Spill` и помечается `|chroma-raw`); часть с собственными настройками выбрасывает все шесть ключей ноды и добавляет после варианта части `|bg:[<transparentBg>,"<mode>","<ключевой цвет>"]` (ключевой цвет остаётся в ключе, как и у ноды), затем `|chroma-raw` для сырого рендера или `|cut:[tol,soft,spill]` для того, что уходит дальше по графу. Её допуск, мягкость и подавление ореола никогда не входят в ключ сырого рендера, поэтому их изменение перевырезает закешированный рендер; перевод части на собственные настройки меняет её ключ, и она устаревшая до следующего запуска. Исполнитель вырезает каждую часть по её действующим настройкам. `ExecuteSingle` выполняет одну ноду, `Cancel()` останавливает после текущей, `assetsPathOverride` перенаправляет финишные ноды (тесты). События (`Editor::PipelineExecEvent`): `NodeState` (`queued`, `running`, `done`, `error`; с `portId` - про одну часть ноды с попортовым запуском: `running`, когда часть действительно начинает считаться, но не при попадании в кеш, затем `done` или `error` с сообщением, всё между `running` и `done` самой ноды), `NodeOutput` (`Editor::PipelineValue` с `previewPath`/`srcPreviewPath`), `Retry`, `Log`, `Done`, `Fatal`. `LoadPreview` и `ClearNodeCache` управляют кешем из редактора. `PipelineNodeWidget::SetParamsOpen` сразу показывает или прячет список параметров карточки (`paramsOpen`, UI-ключ) и у карточки с заданной высотой ставит `size.y = max(minHeight, shown + autoAfter - autoBefore)`, записывая это как изменение размера; `KeepAreaThrough(change)` делает то же для любого изменения содержимого (`PipelineNodeBody::RebuildBodyKeepingArea` для переключателя прозрачного фона, способа, модели, частей вырезания), без привязки к сетке; растягивание держит высоту не меньше `GetAutoHeightForWidth` той ширины, на которой оно закончилось. Холст рисует связи под карточками, затем карточки, затем связи, выходящие из порта, который тело ставит внутри карточки (`PipelineNodeWidget::IsBodyPort`, части ноды вырезания), с теми же цветами и выделением, затем маркеры портов; выбор связи от порядка не зависит. Редактор хранит состояния частей в `PipelineNodeRuntime::portStates` и сбрасывает их, как только нода перестаёт выполняться или стоять в очереди; `PipelineNodeWidget::ApplyRuntime` передаёт каждое изменение состояния телу (`PipelineNodeBody::OnRunStateChanged`), и карточка вырезания обновляет ячейки на месте.

Финишные ноды пишут результат в `<assets>/<assetPath>.<ext>` (при необходимости обрезанный и масштабированный; `keepAspect` вписывает картинку в `resizeW`x`resizeH`, а не растягивает её) и ставят `assetsChanged`; в редакторе исполнитель затем вызывает `o2Assets.RebuildAssets()`, а с `deferAssetsRebuild` (окно Pipeline) сообщает об этом в `Done` и оставляет пересборку окну (см. Фоновая работа и статус).

`Editor::PipelineValue` — `type`, `data` (текст или закодированные байты), `mimeType`; конструкторы `Text`, `Image(bitmap)`, `ImageBytes`, `Bytes`, `GetBitmap()`; `DecodeImageBytes` декодирует PNG/JPEG. `Editor::PipelineUtils` — рабочие пути (`SetWorkPathOverride`), загрузки, data URL, base64, FNV-хеши, hex-цвета, чтение и запись файлов.

`PipelinePairLayout` (`Pipeline/PipelinePairLayout.h`) держит правила «вход | результат», общие с `extractPair` / `cellCorner` AssetsLine: какие типы нод показывают вход рядом с результатом (`IsPairNode`, `InputPortOf`), ширину панелей и высоту строки, сетку вырезания (`ExtractGrid(rowWidth, parts, rowHeight)`: естественная строка вмещает колонки не уже 64 и не ниже 176, карточка с заданной высотой делает её выше; в строке одна часть занимает всю панель, несколько — квадратные ячейки в том числе колонок, при котором они крупнее всего, сетка по центру (`offX`, `offY`), подписи высотой 20 под ячейками; `ExtractCellCorner` даёт положение порта - правый верхний угол картинки ячейки; кнопки перегенерации / удаления ячейки стоят слева сверху, а этот угол вырезан из области клика ячейки), высоту 0 как «автоматическую» (`IsAutoHeight`, `NewNodeSize`, `HeightAfterResize`), `ShowsCompare`, локальную настройку вида (`GetIoView/SetIoView`, `Work/Pipelines/ViewPrefs.json`, версия, по которой открытые редакторы пересобирают такие карточки) и разделитель каждой ноды. В окне `PipelineNodeBody::AddPairRow` добавляет `PipelineIoPair` (панель входа, виджет результата, `PipelineCompareView`); тела image edit и extract ставят результат или сетку частей рядом со сценой рисования (`PipelinePaintEditor::SetBeside`, `SetCompare` для разделённой сцены), а тело вырезания ставит порт каждой части через `GetRowPlacement` + `ExtractCellCorner` (`HasBodyPort`, `GetBodyPortOffset`). `PipelinePairDraw` рисует обрезанные картинки, разделитель в один экранный пиксель и ручку экранного размера (`BadgeScale` = min(размер пикселя, 1.5), `GripRect`).

Тело может само нести входные порты: `PipelineNodeBody::InputsInBody` убирает их из строк портов (вместе со строкой добавления входа), `GetBodyPortOffset` ставит каждый на левый край карточки, а `IsAddInputAt` - строка добавления входа в теле; так делает композер через `PipelineComposerLayersPanel` (`PipelineComposerLayers.h`), чьи закреплённые высоты строк дают положения портов без измерений; `GetAddInputPlace` сообщает, на какой строке добавления стоит точка. `PipelineComposerLayout` (`Pipeline/PipelineComposerLayout.h`) держит правила композера, общие с `shared/composer.ts` / `composerLayout.ts` AssetsLine: строки списка (`Rows`: `+ layer on top`, строки слоёв с раскрытыми настройками, `+ layer below`), размер экспорта слоя (`LayerExportSize`, `HasExportSize`, `TypeExportSide`; `exportW` / `exportH` в `config.layers[id]`, сохраняются при чтении и записи слоя), место нового слоя (`OrderWithNewLayer`, `PlaceNewLayer`: `layerOrder` и `selectedLayer`, их пишут `PipelineEditor::AddCustomInput` и связь, брошенная на строку добавления, в том же шаге отмены, что вход и связь) и `FrameScale` = clamp(1 / масштаб камеры, 0.5, 4), по которому задаются размеры `PipelineComposerFrame` (движковый `FrameHandles` с рукоятками экранного размера) и плашки размера.

`PipelineUpscale` (`Pipeline/PipelineUpscale.h`) держит правила AI-апскейла из `shared/upscale.ts` AssetsLine: `Target` (×2/×3/×4 или размер с замком пропорций, не больше 8192), `ClosestAspect` среди кадров, которые рисует модель, `RenderSizeFor` (1K / 2K / 4K), `RendersLargeSizes` (модели Gemini 3 для картинок, напрямую или через OpenRouter) и промпт. Запрос картинки принимает `AiImageOptions` (разрешение и кадр): Gemini кладёт их в `generationConfig.imageConfig` (`GeminiProvider::BuildImageBody`), чат OpenRouter - в `image_config`, OpenAI выбирает ближайший из трёх своих размеров (`OpenAiProvider::SizeFor`).

`PipelineEditRegion` (`Pipeline/PipelineEditRegion.h`) - рамка ноды правки картинки, по тем же правилам, что `editRegionOf` / `regionBoxes` / `pasteRegionEdit` AssetsLine: `Read` проверяет значение `editRegion`, `Of(node)` читает его у ноды правки, `PixelBoxes` даёт рамку в пикселях и контекстную область, `Weight` - вес смешивания пикселя области, `PasteRegionEdit` вмешивает ответ модели обратно. `PipelineTransparency::Read` сообщает об отсутствии прозрачности у ноды правки с рамкой, поэтому за ним следуют хромакей, запрос прозрачности у модели и `ImageGenerations`. В окне `PipelinePaintEditor::Init(node, withRegion, regionKey, optionalRegion)` хранит рамку под ключом: `roi` у исходника вырезания, необязательный `editRegion` у сцены правки, который создаёт инструмент рамки и убирает её кнопка удаления; `SetDrawingEnabled(false)` (вырезание) убирает панель инструментов и слой рисунка и оставляет рамки редактируемыми, а вырезание переносит рамку выбранной части в `roi`, если пайплайн, сохранённый в другом месте, оставил его рассогласованным. `AiRouter::SetImageStub` отправляет все запросы картинок в функцию вместо провайдера (тесты).

Все точки входа, из которых карточки могут строить виджеты между кадрами (`PipelineEditor::Update`, `OnExecutorEvent`, `PipelineNodeWidget::OnOutputChanged/OnConfigChanged/ApplyRuntime`, `PipelineNodeBody::RebuildBody`, панель слоёв композера), выставляют `PushEditorScopeOnStack`: виджет, созданный вне editor-scope, регистрируется как объект сцены - это засоряло сцену и роняло её при пересборке карточки.

События исполнителя приходят в редактор в главном потоке: корутины исполнителя продолжаются на воркерах (`co_await` запускает дочернюю на `JobThread::Any`), поэтому `onEvent` у `PipelineEditor` передаёт каждое событие задаче главного потока (копию без кэша декодированной картинки, потому что счётчики `o2::Ref` не атомарны), и `OnExecutorEvent` выполняется там.

## Фоновая работа и статус

Окно оставляет главный поток интерфейсу: то, что занимает время, выполняется на воркерах или распределяется по кадрам и показывается, пока идёт.

- **Картинки.** Значение-картинка хранит декодированный растр в слоте, общем для его копий (`PipelineValue::decoded`, `ShareDecoded`, `PeekBitmap`); редактор даёт слот каждому значению, которое хранит (`LoadPreview`, `OnExecutorEvent`, `RefreshSourceOutput`), так что картинка декодируется один раз, сколько бы карточек её ни показывали. Карточки просят её через `PipelineNodeBody::Picture` → `PipelineEditor::GetPicture`: ещё не декодированную `PipelineImageLoader` декодирует на воркере вместе с копией не больше 1024 px, карточка тем временем показывает `loading..`, а `ApplyDecodedPictures` между кадрами в пределах 6 мс отдаёт результаты и вызывает `OnOutputChanged` у карточек, которые просили. `PipelineDisplayCache` держит одну текстуру размера карточки на растр для всех видов (картинки, пары и сравнения, сцена рисования, слои композера). Картинки источников для карточек читаются без декодирования (`ResolveSourceValue(..., decodeImage = false)`). Холст рисования (image edit, paint), чья картинка ещё декодируется, тем временем не раскладывается (`PipelinePaintEditor::SetBackground(bitmap, pending)`): сохранённый рисунок загружается один раз, в размере картинки. Карточки аудио и видео делят один `SoundAsset` на клип, так как ассет остаётся в кэше ассетов до конца сессии.
- **Запуски.** `ExecuteWork` / `ExecuteSingleWork` (входы, нода, её превью, запись кэша, сигнатуры) выполняются на воркере; в главный поток возвращается только `FinishRun`. Редактор включает `deferAssetsRebuild`: `Done` запуска несёт `assetsChanged`, и ассеты пересобираются один раз, после последнего запуска в очереди, в фоне (`Assets::RebuildAssetsInBackground`); сохранение ассета (`IAssetEditorWindow::SaveEditingAsset`) и сохранение слоёв композера пересобирают так же. Превью видео читают атлас кадров в своём потоке.
- **Карточки.** Undo, redo, перезагрузка, удаление и вставка меняют только свои карточки (`SyncGraphTo`, `AddCard`, `RemoveCard`); переименованный слой композера и переименованная часть extract оставляют карточку и её строки. Карточки вне вида после открытия раскладываются по несколько за кадр (`WarmUpCards`, 2 мс за кадр). Сдвинутая камера пишется в документ ассета через 0.25 с после остановки. Связи кадра собираются один раз для обоих проходов (`CollectEdgeDraws`).
- **Статус.** `PipelineEditor::GetBackgroundStatus()` (`Loading previews 12/150`, `Applying Outline`, `Rebuilding assets`) показывается в панели окна; карточка, занятая фоновой работой (`PipelineNodeWidget::IsBusyInBackground`: применяется её эффект, декодируются её картинки), рисует тонкую бегущую полоску под заголовком.

`PipelinePerfUiFixture.*` в `o2EditorUITests` замеряет основные действия на больших пайплайнах проекта (`O2_PIPELINE_PERF=1` или папка проекта, результаты JSON в `O2_PIPELINE_PERF_OUT`); `PipelineResponsivenessUiFixture.*` держит поведение выше.

## AI image to UI

`imageToUi` (`Pipeline/Nodes/ImageToUiNode.*`, ядро в `Pipeline/UiLayout/`, пространство имён `Editor::UiLayout`) работает как [XuToWei/Image-To-UI](https://github.com/XuToWei/Image-To-UI): его скилл запускается **без изменений** (Python), а модель зрения выступает агентом, для которого скилл написан. Нода делает то, что скилл считает данным, - папку нарезанных спрайтов, вырезанных из макета, - отвечает на вызовы модели агента и превращает папку задачи скилла в выходы. Это порт `backend/src/uiLayout/run.ts` AssetsLine, контракт хоста - `o2/Tools/ImageToUi/PORTING.md`. `PipelineImageToUi` (`Pipeline/PipelineImageToUi.h`) держит то, о чём договорились три редактора (`shared/imageToUi.ts` AssetsLine): значения по умолчанию, `ReadConfig` (`maxTurns` 4..120, карточка предлагает `TurnOptions` 20 / 40 / 60 / 90 / 120, по умолчанию 60), `SpriteName` (`preview` / `layout` становятся `sprite_<key>`), `SpritePorts`, `SummarizeLayout` (спрайты - различные `asset`), `ReadRunSummary` (`summary` трейса), `RunLine`, `SummaryLine`.

**Выходы, которые решает запуск.** Схема с `dynamicOutputs` запускается один раз на все выходы (`PipelineRunResult::outputs` по имени, `order` - порядок запуска) в `PipelineExecutor::EvaluateDynamic` (`PipelineExecutorDynamic.cpp`). Результат - пакет под сигнатурой ноды: `content/<sig>-outputs.json` = `{"outputs":[{name,type,key,ext}]}` и по файлу на выход под `BundleKey(sig, name)` = первые 32 hex-цифры sha256(`<sig>#<name>`); загрузка без любого из файлов - промах, на пайплайн и сигнатуру идёт одно вычисление за раз, обход (↻) удаляет пакет и выставляет `ctx->fresh`, `cachedOnly` сообщает `Not cached`. `DynamicPorts` даёт порты: сначала выходы схемы, затем остальные в порядке запуска; выход, который у ноды уже есть, сохраняет id порта, новый получает id схемы или `sp-<name>` (символы вне `[A-Za-z0-9_-]` - `_`). Исполнитель шлёт `NodePorts`; `PipelineEditor::ApplyNodePorts` даёт живой ноде эти выходы, убирает связи ушедших портов, перестраивает карточку и сохраняет пайплайн без шага отмены. Первый выход - превью ноды, каждый остальной - превью порта (картинки `.png`, разметка `.txt`), устаревшие превью портов удаляются. Контекст несёт `workDir` (`Work/Pipelines/cache/<pipeline>/work/<node>/`, трейс), `fresh` и `memoGet` / `memoPut` (ответы моделей, запомненные в папке контента под ключами `uil-t-` / `uil-i-`: первые 40 hex-цифр sha256 по частям, каждая с NUL в конце). Ключ кэша потребителя динамического выхода - `PipelineGraph::DynamicPortSignature(sig, port)`, так что два выхода никогда не делят слот. Синхронизация отправляет выходы 1..n частями `<node>#<port>` с расширением по типу порта и засевает скачанный результат как пакет (`AssetsLineSyncResults::SeedBundle`), так что запуск, сделанный в вебе, экспортируется здесь без повторных вопросов моделям.

**Python** лежит в `o2/Tools/ImageToUi/`: `upstream/` (скилл, не правится), `agent/agent.py` (окружение агента) и `PORTING.md`, их копирует из `AssetsLine/image-to-ui/` скрипт `tools/sync-image-to-ui.sh` (o2-Template). `ImageToUiHome` находит его от корня проекта или вверх от рабочей папки (`O2_IMAGE_TO_UI_DIR` переопределяет). Интерпретатор - настройка пайплайна `imageToUiPython` (`Python 3` в диалоге AssetsLine); пустая - `FindPython` берёт первый из `python3` в `PATH`, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, который импортирует Pillow и numpy (проба кэшируется по `PATH`), иначе первый найденный - тогда агент выходит с кодом 3 и его `detail` (что поставить) становится ошибкой ноды.

**Запуск** (`UiLayoutRun.cpp`): анализ (`Prompts::Analyze`, `ParseAnalysis`: id, сетки развёрнуты в ячейки с их текстами), замер текстов по чернилам (`UiLayoutMeasure`; только для того, что нарезка должна стереть), `PlanLooks` и нарезка (`CutAll`, по четыре сразу, у каждого воркера свой `ParallelAiCtx`; `UiLayoutSlice`, `UiLayoutMatte`: кроп, цвет ключа, рендер моделью, хромакей, совмещение, деформация, despill, композит, заливка остатков, поля nine-slice для панелей; плохая матте режется ещё раз с другим сидом), фон (`MakeBackground`: цвет или подложка, проверенная `PlateLeftovers`, запрошенная ещё раз и залитая `HarmonicFill`). Затем входы скилла в `<workDir>`: `input/design.png` (сведённый на белый) с тремя файлами Roboto рядом, плоская `sprites/<name>.png` (`AssetFileName`: ключ вида в безопасном виде плюс `panel_` / `button_` / `bar_` / `icon_`, если ключ этого не говорит; повторы `_2`), `<name>.png.meta` с `spriteBorder` Unity для видов с nine-slice (`NineSliceMeta`), `sprites/bg_backdrop.png` для подложки, `fonts/Roboto-*.ttf` + `LICENSE-Roboto.txt`, свежие `task/` и `agent-view/`. Трейс сбрасывается на диск, агент работает, трейс перечитывается (агент дописал свои шаги), и выходы - `task/reconstruction.png` (`preview`), `task/ui_structure.json` байт в байт (`layout`) и по картинке на каждый спрайт, который называет разметка (`AssetRefs`: каждый `asset`, со состояниями), в порядке папки. Результат с `ok: false` роняет ноду (`the agent ended without a checked layout (<error или status>)`); незавершённый запуск всё равно отдаёт выходы, лог и трейс говорят NOT completed с блокерами. Шаги пишутся в `<workDir>/trace/trace.json` с картинками по ходу дела (`Trace`).

**Агент** (`UiLayoutAgent.*`): `AgentProcess` запускает `<python> -B agent/agent.py --design … --assets … --output … --scratch … --skill upstream/image-to-ui --max-turns N --name=… --hint=… --sprites-note=… --font fonts/Roboto-Regular.ttf --font fonts/Roboto-Medium.ttf --font fonts/Roboto-Bold.ttf --trace-dir …` (`AgentArguments`, свободные тексты как `--key=value`) через `posix_spawn` в `<workDir>`, в своей группе процессов и с неблокирующими пайпами (только POSIX; на других платформах нода падает с `cannot run on this platform`). `RunAgent` опрашивает пайпы раз в кадр: строка stdout `@@bridge {"type":"model","id","tag","prompt","images"}` получает ответ в stdin `{"id","text"}` или `{"id","error"}` через `AiText` (тег `agent <tag>`, память по модели, промпту и байтам картинок, JPEG уходит как `image/jpeg`), `event` пишется в лог, `result` - последняя строка; stderr хранит последние 8000 байт для ошибки агента, остановившегося без результата. Отменённый запуск убивает группу процессов.

**Экспорт** (`UiLayoutExport.cpp`, `UiLayoutWidgets.cpp`, `UiLayoutResolve.cpp`, `ImageToUiExport`): после свежего запуска и по `Save to Assets` прототип собирается из `ui_structure.json` скилла и выходов-спрайтов (их поля nine-slice - из запуска или из `.png.meta` рабочей папки) и сохраняется как `ActorAsset` в `Assets/<assetPath>/<screenName>.proto` (существующий перезаписывается на месте: сохраняются его uid и id акторов по пути), с `<screenName>_Resources/Sprites/<name>.png`, `white.png` для ровных цветов, `Fonts/Roboto-*.ttf` и их лицензией, `FontStyles/*.fntstyle` с `FontStrokeEffect` для текста с обводкой. `PlanWidgets` читает структуру так, как её рисует скилл: `SnapshotStructure` применяет текущий вариант каждого блока состояний и подписи прогресса (`FormatProgress`), `ResolveStructure` - порт `layout.py` (раскладки row / column / grid с отступами, промежутками и распределением, `align` / `vAlign` / `offset`, `responsive`, смещения прокрутки), каждый бокс крепится к точке своего `anchor`, блок `responsive` становится якорями и отступами o2. Виджеты: `container` - `Widget` (со своим `asset` или `color`), `image` - `Image` (`color` его тонирует), `rect` / `overlay` - `Image` тонированного белого спрайта, `button` - `Button`, `text` - `Label` (`fontFamily` по насыщенности, `fontSize` в пикселях как `round(fontSize·72/92)` пунктов, `alignment`, `textVAlign`, `color`, обводка), `fill` прогресса - `HorizontalProgress` / `VerticalProgress` по `direction` с долей значения, сетка с одним промежутком - `GridLayout`; `nineSlice` true / `auto` / `meta` берёт поля из `.png.meta` (иначе четверть меньшей стороны, 4..60, как `render_comparison.py`), число - все стороны, объект - свои стороны; `opacity` - собственная у ноды (визуальный слой контейнера), `visible: false` выключает виджет; явные глубины отрисовки на слое `UI`. Не воспроизводится и пишется предупреждениями: раскладки row / column (запекаются позициями), сетки с двумя промежутками или сдвинутыми ячейками (запекаются), остальные варианты состояний (запекается текущий), окна прокрутки (запекаются со своим смещением), `hueShift`, `textScaleX`, `lineHeight`, безопасные зоны, дети заполнения прогресса (не обрезаются; само заполнение масштабируется, а не обрезается); надписи выравниваются по строке o2, скилл выравнивает видимые чернила. `.proto` пишет только редактор, которому принадлежат ассеты.

**Окно**: `PipelineImageToUiBody.cpp` (карточка: пара, итог `completed · 3 checks · 9 elements · 3 sprites` / `not completed · 2 blockers · …` по разметке и `summary` трейса, сетка спрайтов с портами на углах ячеек - `HasBodyPort` / `GetBodyPortOffset`, строки экспорта, параметры с `Agent turns`; `AddModelRow` принимает ключ конфига и подпись), `ImageToUiDebugDlg.*` (окно отладки: виды `input`, `analysis`, `sprite`, `background`, `measure`, затем шаги агента `prepare`, `view`, `write`, `check`, `target`, `preview`, `finalize`, `agent` и `output`; ход агента (`turn-<n>`) показывает заметку модели, её действие (`data.action`) и текст результата; картинки `prepare` / `measure` / `check` / `target` / `preview` / `finalize` / `view` показываются во всю ширину; после проверки или цели дизайн и картинка с заголовком `reconstruction.png` делят один разделитель; заголовок говорит `completed · N checks` или `not completed · N blockers`; `debugView` / `debugStep` - ключи только для UI).

Тесты: `ImageToUi*` и `DynamicFixture.*` в `o2EditorTests` (JSON, промпты и ключи памяти против эталонных хэшей, анализ веб-запуска, помощники модели, nine-slice, имена файлов ассетов, `AssetRefs`, заметка о спрайтах и `.png.meta`, конфиг и итог карточки; `ImageToUiLayout.*`: каждый бокс против собственных `layout.py` и snapshot скилла (запускаются найденным Python), форматы прогресса Python, план виджетов; `ImageToUiAgent.*`: командная строка, пакет, дочерний процесс; `ImageToUiRun.*`: вся нода через исполнитель с подменёнными моделями и агентом по сценарию (`tests/Pipeline/ImageToUiTestKit.h`: структура из `task/assets/assets_inventory.json`, check, `alignment_review.md` с привязкой ревью и строкой на каждый путь легенды, finalize), который доводит настоящий скилл до `complete: true` - порты, разметка байт в байт, входы скилла, трейс, боксы против `render_trace.json`, экспорт, кэш, ↻ - и отказы (агент без проверенной разметки, Python без зависимостей); `ImageToUiFixture.*` проигрывает нарезку записанного веб-запуска), `ImageToUiUiFixture.RunsTheSkillThroughTheEditor` в `o2EditorUITests` (тот же запуск через редактор: карточка, окно отладки, прототип, повторный экспорт, кэш) и `AssetsRebuild.NewNestedFoldersAppearAtOnce`. Тестам запуска нужен Python 3 с Pillow и numpy, без него они пропускаются; фикстура не лежит в репозитории: `O2_IMAGE_TO_UI_FIXTURE=<dir>` или `Work/ImageToUiFixture/`.

## Синхронизация с AssetsLine
`Editor::AssetsLineSync` (`o2/Editor/Sources/o2Editor/Pipeline/Sync`) держит ассеты пайплайнов одной папки и связанный проект AssetsLine в согласии; им владеет `EditorApplication` и вызывает `Update` каждый кадр, окно Pipeline даёт ему `isPipelineFileBusy` (у открытого ассета несохранённые правки), `onPipelineFileChanged` (перечитать открытый ассет) и `onResultsChanged` (перечитать превью) и само сохраняет синхронизируемый пайплайн через секунду после правки. Связь - `o2::AssetsLineConfig` в `o2Config.assetsLine` (`enabled`, `serverUrl`, `projectId`, `projectName`, `folder`, `writeFinishAssets`, `pollInterval`); токен и состояние синхронизации - у пользователя в `Work/Pipelines/sync/` (`credentials.json`, `state.json`, `base/<id>.json`).

`AssetsLineClient` отправляет запросы (`Authorization: Bearer`, `X-Project-Id`, `X-Sync-Client`) через `o2Network`. Подключение: `StartConnect` получает у сервера код и открывает страницу подтверждения, затем опрашивает, пока не придёт токен; `ConnectWithToken` проверяет токен, созданный вручную, через `/api/sync/me`.

Проход (`SyncPass`, корутина) читает `/api/sync/state`, затем:
- **документы** (`SyncDocuments`): сканирует папку (файл без id берёт UID из meta, скопированный файл получает новые id, источник-ассет получает id выгрузки по содержимому), сравнивает каждый пайплайн с его базой (последней версией, общей для обеих сторон, без камеры) и сохранённой ревизией: отправляет локальную правку с `baseRev` (сервер сливает её с правками, сделанными тем временем, если пришла база; слитый ответ записывается обратно, если файл не поменялся снова), забирает удалённую правку, переименовывает и удаляет с любой стороны; файлы, которые редактор держит несохранёнными, пропускаются;
- **результаты** (`SyncResults`, когда сдвинулся счётчик результатов сервера или локальный файл): сопоставляет ключи результатов AssetsLine (`<node>`, `<node>.src`, `<node>#<port>`, `<node>.raw` / `<node>#<port>.raw` - сырой рендер chroma-ноды или части, чьи действующие настройки - хромакей) с файлами превью и контента в `Work/Pipelines/cache/<id>/`, выгружает изменённое здесь и скачивает изменённое там (изменено с обеих сторон - побеждает актуальный), обменивается выгрузками источников, помечает актуальным на другой стороне то, что актуально на этой - нода, актуальная на сервере, получает скачанное в кэш контента под ключом, по которому его ищет локальный запуск (`PipelineExecutor::ContentSignature`); перегенерированная с любой стороны нода сохраняет сигнатуру, поэтому пришедший результат заменяет хранимую генерацию, а отправленный отсюда снова помечается актуальным, чтобы сервер сделал то же самое, - и пишет результаты финишных нод в ассеты (скачанные или посчитанные запуском финишной ноды только из кэша).

Тесты: `PipelineFormat.*` (формат, seed, круговая запись документов AssetsLine, найденных на машине), `AssetsLineSync_.*` (сквозные против настоящего сервера: задать `O2_ASSETSLINE_TEST_URL`, одноразовый поднимается `AssetsLine/backend/scripts/test-instance.sh start`), `PipelineSyncUiFixture.*` в `o2EditorUITests` (автосохранение, перечитывание, диалог).

## Импорт
`PipelineImport::ParseBytes` читает экспорт AssetsLine по содержимому: JSON пайплайна, JSON-бандл с результатами в data URL (`Parse`) или ZIP-бандл (`ParseZip`: `pipeline.json`, необязательный `manifest.json` со списком `results/<файл>` по нодам с типом и mime - запись с ключом `<nodeId>#<portId>`, называющая оба, это одна часть попортовой ноды - и `uploads` с файлами, которые читают ноды-источники; файлы вне манифеста берутся по имени `results/<nodeId>.<ext>`) в `PipelineGraph` со свежим `id` и карту результатов `PipelineValue`; `StoreResults` записывает их как превью, записи кеша содержимого и отметки актуальности для id пайплайна - сначала загрузки, потому что нода-источник хеширует то, что читает, затем части попортовой ноды под их собственными превью портов и сигнатурами (`PipelineExecutor::PortSignature`); `ImportFile` создаёт ассет в папке, сохраняет результаты под id графа и пересобирает ассеты. `PipelineZip` - небольшой читатель и писатель архивов под этим (записи stored и deflate, zlib).

`O2_PIPELINE_RUN=<файл>` прогоняет ассет `.pipeline` без редактора - тестом `PipelineRunAsset.RunFile` из `o2EditorTests`: выполняются все цели запуска графа с настоящими провайдерами, поэтому арт-пайплайн можно гонять из командной строки вместо окна Pipeline (`O2_PIPELINE_NODE` ограничивает запуск одной нодой, `O2_PIPELINE_ASSETS` задаёт папку, куда пишут финишные ноды, `O2_PIPELINE_WORK` - где лежит кеш, `O2_PIPELINE_TIMEOUT` - бюджет одной цели в секундах).

`O2_PIPELINE_IMPORT=<файл>` заставляет окно Pipeline импортировать этот экспорт AssetsLine на первом обновлении (отладочный ключ, чтобы воспроизводить проблемы импорта без файлового диалога); `PipelineWindow::ImportFile` ловит исключения и показывает их в строке статуса.

`id` графа - ключ кеша, которым пользуется редактор (`PipelineEditor::GetPipelineId`); ассет без id при открытии берёт свой UID, поэтому результаты, закешированные по UID до появления поля, остаются доступны, а граф, сохранённый в другой ассет, сохраняет свой кеш.
