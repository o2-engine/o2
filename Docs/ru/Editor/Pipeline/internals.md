# Пайплайны

AI-пайплайны контента: графы нод, которые превращают текст, картинки и звуки в ассеты через API провайдеров и локальную обработку. Исходники - в `o2/Editor/Sources/o2Editor/Pipeline` (пространство имён `Editor`); редакторская часть - окно Pipeline. В рантайме остаётся только `o2::PipelineAsset` - ассет `.pipeline`, хранящий граф как `DataDocument`; `PipelineGraph::LoadFromAsset` / `SaveToAsset` переводят документ в граф редактора и обратно. Документ - JSON пайплайна AssetsLine (см. Формат).

> **Менять вместе.** Редактор пайплайнов есть и в AssetsLine: его веб-редактор и сервер (`AssetsLine/`: `shared/`, `backend/src/`, `frontend/src/nodeEditor/`) и его плагины для редакторов, помимо этого редактора o2 (`o2/Editor/Sources/o2Editor/Pipeline/` и `o2/Editor/Sources/o2Editor/Windows/PipelineWindow/`). Все они читают и пишут один и тот же документ `.pipeline` и синхронизируют пайплайны друг с другом. Изменение поведения пайплайна, типа ноды, ключа конфига, формата файла, правил исполнителя и кеширования или интерфейса нод нужно вносить во все сразу, обновляя их тесты и документацию, - иначе синхронизированные пайплайны разойдутся. Части, зависящие от движка, у каждого редактора свои: здесь AI UI layout сохраняет только прототип o2.

## Внешний вид окна

`Windows/PipelineWindow/PipelineTheme.*` хранит две палитры (тёмная - токены AssetsLine, светлая - цвета редактора o2) под именами CSS-токенов, общими с AssetsLine, текущую тему (тему редактора; `SetKind` подменяет её для тестов и галерей, `FollowEditor` снимает подмену) и версию, которую опрашивает редактор: при смене `PipelineEditor::ApplyTheme` перестраивает карточки и перекрашивает меню. `PipelineDraw` рисует сглаженные скруглённые заливки, обводки с градиентом и почти гауссовы тени (кольца на ±2σ) с каймой в один пиксель цели; шахматка (подложки картинок, сцена композера) - одна текстурированная скруглённая сетка с повторяющейся плиткой 2 × 2 текселя, а точки холста, пока они чаще 32 пикселей, - один квад с плиткой из десяти на десять клеток, пересобираемой при смене зума: квадами при отдалении их были сотни тысяч на кадр. Контролы (`PipelineThemeControls.cpp`: поля, кнопки, переключатели, сегменты, списки, меню) собраны из этих примитивов, а не из спрайтовых стилей редактора; `PipelineRichText` раскладывает текстовые результаты в Markdown (абзацы через 0.5 em, `**жирное**` полужирным начертанием). Метрики карточек и тел следуют константам AssetsLine (`frontend/src/nodeEditor/constants.ts`, `nodeRenderers.tsx`: GAP 7, поле 14 + 16.1·строк, кнопки 27.52, свёрнутый список 31.84, строки fx через 6). Закрытый переменными окружения UI-тест `PipelineThemeGallery` снимает каждую карточку бандла AssetsLine там же, где она стоит в веб-эталоне, с дампом блоков (`PipelineLayoutDump`) для попиксельного и поблочного сравнения.

## Граф

- **Editor::PipelineGraph** — `nodes`, `edges`, сохранённая камера. `Validate()` сообщает о несовпадении типов и циклах, `WouldMakeCycle(from, to)`, `FindEdgeToPort`, `GetOutgoingEdges`, `RemoveDanglingEdges`, `ResolveSeeds()` (ноды картинок наследуют seed ноды-картинки выше по графу при `inheritSeed`), `ComputeSignatures()` — хеш содержимого каждой ноды из её конфига (без UI-ключей, см. `GetUiOnlyConfigKeys()`), сигнатур нод выше по графу и seed.
- **Editor::PipelineNode** — `id`, `nodeType`, `position`/`size` (ось y вниз, как в веб-редакторе), `inputs`/`outputs` (`Editor::PipelinePort`: `id`, `name`, `portType`, `custom`), `config` — `DataDocument` с `GetConfigString/Number/Bool/Value`, `SetConfig*`, `RemoveConfig`, `HasConfig`. Добавленные пользователем входы хранятся в `customInputs` (`GetCustomInputs/SetCustomInputs`); `PipelineNodeRegistry::SyncNodeWithSchema` пересобирает список портов из схемы и пользовательских входов.
- **Editor::PipelinePortType** — `Text`, `Image`, `Video`, `Audio`, `UiKit`, `TextStyle`; связь соединяет только порты одного типа. `UiKit` и `TextStyle` (в файле `uiKit` / `textStyle`) — JSON-документы, которые хранятся и синхронизируются как текст (`IsTextLikePortType`, `PipelineValue::TextOf`, файлы `.txt` в кеше и превью); неизвестный тип по-прежнему читается как `text`.
- **o2::PipelineAsset** (движок) — ассет `.pipeline` с документом графа; редактор читает его в `PipelineGraph` и записывает обратно при каждом изменении.

## Формат
Файл `.pipeline` - это документ `Pipeline` AssetsLine: `schemaVersion`, `id`, `name`, `nodes` (`id`, `type`, `position`, `size` как `{width, height}`, `config`, `inputs`/`outputs` из `{id, name, type, color?, custom?}`), `edges` (`id`, концы, `points`), `camera` (`{x, y, scale}`: экран = мир * scale + (x, y)). `PipelineGraph::LoadFromJson` / `SaveToJson` (и `LoadFromJsonString` / `ToJsonString`, их же используют отмена и буфер обмена) читают и пишут его; поля, которые редактор не использует - `annotations`, `icon`, `color` порта, всё более новое - хранятся в `extra` графа, ноды и связи и пишутся обратно без изменений. Целые числа пишутся целыми, остальные округляются до 1/1000, поэтому документ, прочитанный и записанный без правки, не меняется побайтно. Камера пересчитывается через фиксированный номинальный вид (`GetNominalViewSize`). Старый формат o2 (`{"graph": ...}`, рефлексия) распознаётся `IsLegacyDocument`, читается и при следующем сохранении пишется в новом формате.

Числа, которые оба редактора выводят из документа, совпадают: неявный seed - как в AssetsLine (32-битный FNV-1a от id ноды, семантика `Number()` для `config.seed`, наследование выключено только буквальным `false`), список UI-ключей конфига одинаков. Финишная нода без `assetPath` пишет в `Generated/<filename>` (`PipelineNodeRegistry::GetFinishAssetPath`). Вставка даёт нодам и портам новые id и переназначает id, на которые ссылается конфиг (`PipelineNode::RemapConfigPortIds`: пользовательские входы, слои composer, регионы extract).

## Типы нод

`Editor::PipelineNodeRegistry` хранит все `Editor::PipelineNodeSchema` (`type`, `label`, `category`, `description`, `inputs`, `outputs`, `addableInputs`, `instant`, `perPortRun`, `dynamicOutputs`, `defaultSize`) вместе с реализацией (`Editor::PipelineNodeBase::Run` — `Coroutine<PipelineRunResult>`, получающая контекст выполнения и значения входов). `AllSchemas()`, `GetSchema(type)`, `CreateNode(type, position)`, `IsFinishType`. Кроме `Run` реализация может переопределить `InitNode(node)` (конфиг, с которым создаётся нода), а для ноды с `perPortRun` - `SyncPorts(node)` (она сама владеет списком выходов, и `SyncNodeWithSchema` не трогает выходы схемы), `PortCacheExcludedKeys()` и `PortCacheVariant(node, portId)` - ключи конфига, которые выбрасываются из попортовой сигнатуры, и то, что добавляется в неё для конкретного порта.

`Editor::PipelineRegions` - список частей ноды вырезания: `PipelineExtractRegion` (`id` - id выходного порта с этой частью, `name` - что вырезать и имя порта, нормализованная рамка, `ownTransparency` - есть ли у неё собственные настройки фона), `Read`/`Write` по конфигу ноды (нода, сохранённая до появления частей, читается как одна часть из `prompt` и `roi`; `Write` оставляет члены части помимо id, имени и рамки - её собственный `transparency`, всё более новое - у части с тем же id), `PortNames` (уникальные, непустые), `SyncPorts` (пересобирает выходы, сохраняя id, поэтому связи переживают переименование; у ноды без списка частей остаётся ровно один выход с именем `out` - её первый порт со связями, остальные удаляются, - потому что AssetsLine ищет этот выход по имени из схемы и добавлял фантомный `out` рядом с портом, названным по промпту), `RegionOfPort`, `FindTransparency(node, portId)` (собственные настройки фона части, null, если она следует ноде), `SetOwnTransparency(node, portId, own)` (даёт части полную копию её действующих настроек или убирает её), `autoSplitPrompt` и `ParseAutoSplit(answer)` (модель отвечает `box_2d` в виде `[ymin, xmin, ymax, xmax]` на сетке 0..1000; найденные так части начинают без собственных настроек). Вставка переназначает id частей на месте, поэтому часть сохраняет настройки при копировании.

**Фон по частям.** Часть может нести `transparency` - шесть ключей `transparentBg`, `transparentMode`, `chromaColor`, `chromaTolerance`, `chromaSoftness`, `chromaSpill` (`PipelineTransparency::SettingKeys()`), записанных целиком в момент перевода части на собственные настройки. Если объект есть, он заменяет эти ключи ноды для этой части; ключ, которого нет в неполном объекте, берётся у ноды, затем по умолчанию (`false`, `twoPass`, `#00b140`, 30 / 15 / 60). Всё, что читает их для запуска, идёт через действующие настройки части: `PipelineTransparency::SettingValue(node, portId, key)`, `Read(node, portId)` (промпт вырезания, два прохода или хромакей), `UsesChromaPostStep(node, portId)`, `ApplyChromaPostStep(node, raw, portId)`, `AnyChromaPostStep(node)` (автоприменение ползунков вырезания в редакторе), `ImageGenerations(node)` (число генераций одного запуска: на часть две для прозрачного рендера в два прохода, иначе одна - это число AssetsLine умножает в цену на кнопке запуска; редактор o2 цену не показывает) и сырые рендеры в синхронизации.

**Фон, который делает модель.** `PipelineTransparency::SupportsNativeTransparency(model)` отвечает по id без пробелов по краям и начального `models/`, в любом регистре: да для `gpt-image…` (OpenAI), для `openai/gpt-image-…`, кроме `openai/gpt-image-2` и его датированных снимков `openai/gpt-image-2-YYYY-MM-DD`, для `openai/gpt-5-image`, `openai/gpt-5-image-mini` и `sourceful/riverflow-v2.5-pro`; нет для всего остального. Режим решает id, сохранённый в ноде; вызов с прозрачным фоном берёт затем только маршруты, чей собственный id его рисует (`RoutesFor(model, true)`), и если ни для одного нет ключа, родной провайдер сообщает об отсутствии своего. Для них `Read` даёт действующий `mode` `native`, что бы ни было в `transparentMode`, а способ из конфига хранит в `storedMode`; конфиг не переписывается, поэтому `WriteSettings` и часть `bg:[...]` сигнатуры порта берут `storedMode`. `UsesNativeTransparency(node, portId)` истинно, когда фон включён (для `aiRemoveBg` всегда) и режим `native`. Такая нода или часть не хромакейная: `UsesChromaPostStep` / `AnyChromaPostStep` ложны, поэтому исполнитель не хранит сырой рендер, не добавляет вариант `chroma-raw` и ничего не вырезает, ползунки вырезания не запускают автоприменение, а `ImageGenerations` считает одну генерацию. Ноды делают один вызов с `transparentBackground` в `AiRouter::GenerateImage`. `OpenAiProvider` кладёт `"background": "transparent"` в тело `images/generations` и поля `background` и `output_format` в форму `images/edits`; `OpenRouterProvider` отправляет вызов в свой images API с `background` и `output_format` в теле (`BuildImagesBody`: `model`, `prompt`, `n`, референсы в `input_references`, без seed и размера); Gemini флаг игнорирует. Промпты не называют цвет подложки (`nativeBackdrop`, `nativeEditSuffix`); `imageExtract` обрезает ответ по альфе и возвращает его необрезанным, если в нём нет ни одного видимого пикселя.

Категории: источники (`sourceText`, `sourceImage`, `sourceAudio`), преобразования (`textCompose`, `textConcat`, `drawImage`, `imageOutline`, `imageShadow`, `imageGradient`, `imageColor`, `audioProcess`), AI (`aiText`, `textEdit`, `promptGen`, `nanoBananaGen`, `imageEdit`, `imageExtract`, `removeBackground`, `aiRemoveBg`, `aiUpscale`, `videoGen`, `sfxGen`, `ttsSpeech`, `musicGen`), выходы (`composer`, `finishImage`, `finishText`, `finishVideo`, `finishAudio`). Ноды с `instant` выполняются локально и автоматически перезапускаются редактором - от результатов, которые показывают их входы (`PipelineExecutor::ExecuteSingle`): перегенерированная нода сохраняет сигнатуру, и сохранённый результат эффекта мог быть сделан из старой картинки. Запуск только из кэша всё равно считает источники - они лишь читают свой файл.

Провайдеры (`o2/Pipeline/Providers`): `GeminiProvider` (текст, генерация и правка картинок, Imagen, TTS, музыка Lyria), `OpenAiProvider` (текст через chat completions, картинки через `images/generations`, а с референсами - через multipart `images/edits`), `OpenRouterProvider` (текст и картинки на любой модели OpenRouter через chat completions API; картинки ещё и через images API `POST /images`, куда идут вызов с прозрачным фоном и модели, умеющие только картинки: вызов chat completions, получивший 404, повторяется там), `ElevenLabsProvider` (речь, звуковые эффекты), `VideoProviders` (Veo, Kling), `LocalAgentProvider` (текст и зрение на агенте этого компьютера: `local:claude-code[:<модель>]` один раз запускает Claude Code, `ClaudeInvocation` собирает экономный вызов `claude -p` - stream-json на входе и выходе, `--tools ""`, однострочный `--system-prompt`, `--strict-mcp-config`, `--no-session-persistence`, `--disable-slash-commands`, `--bare` с `ANTHROPIC_API_KEY`, когда задан API-ключ, `MAX_THINKING_TOKENS=0`, если размышления не включены, картинки блоками base64 в единственном сообщении пользователя - а `ParseClaudeOutput` читает его строку `result` (токены, `total_cost_usd`, `is_error`); `local:codex[:<модель>]` один раз запускает Codex, `CodexInvocation` собирает `codex exec --json --ephemeral --skip-git-repo-check --ignore-user-config --ignore-rules --sandbox read-only -C <папка>` с `--disable` apps, multi_agent, goals, shell_tool, plugins, view_image (и image_generation для текста), `--enable omit_skill_descriptions`, `-c model_instructions_file=<одна строка>`, `web_search="disabled"`, `model_reasoning_summary="none"`, `model_reasoning_effort`, картинками `--image=<файл>` (по одному значению: `-i` забирает все аргументы после себя), промптом в stdin, без `OPENAI_API_KEY`, с `CODEX_API_KEY` из настроек или без него, папкой исполняемого файла и папками Homebrew в начале `PATH` (codex - скрипт node); `ParseCodexOutput` читает события JSONL (`thread.started`, элементы `agent_message`, расход `turn.completed`, `turn.failed`, `error`); `local:codex-image` (`GenerateImage`) один раз просит `image_gen` (`CodexImagePrompt`: кадр, размер, прозрачность текстом) и берёт самую новую картинку из `CODEX_HOME/generated_images/<thread_id>` (`FindCodexImage`), удаляя эту папку; `local:command` запускает `sh -c <localCommand>` с промптом и путями картинок в stdin; все через `UiLayout::AgentProcess` (`Start` принимает переменные окружения `NAME=value`, голое `NAME` убирает переменную, `CloseInput` закрывает stdin) в пустой папке системного temp (`RunCall`); `OfferedModels` / `OfferedImageModels` - то, что меню текстовых / картиночных моделей добавляют при `localAgentEnabled`, каждого агента - только когда его находит `FindClaude` / `FindCodex`, полным путём; `LocalAgentSetup` проверяет агента в фоне (`Check`: не установлен, ключ API в настройках, иначе `claude auth status --json` / `codex login status`, которые читают `ClaudeStatusOf` / `CodexStatusOf`, затем каталог Codex `codex debug models --bundled` один раз за сессию, `CodexModelsOf`) и настраивает его (`SetupScript` - установить, если нет, войти, если не вошёл, - пишется файлом `.command` и открывается в Terminal через `OpenSetup`, на Linux - `x-terminal-emulator` и подобные; `SetSetupOpener` подменяет терминал в тестах); окно настроек `AssetsLineDlg` - по вкладке на раздел (`Page`: Sync, Keys, Agents, Editor; `Show(Page)`), на вкладке агентов - по карточке на агента (`AgentCard`: проверка, состояние, кнопки настройки и проверки, выпадающие списки модели / размышлений или effort / аккаунта, строка ключа)). Текстовые и картиночные ноды и `Auto split` ноды extract вызывают `AiRouter`, который выбирает провайдера и его ключ по id модели. `FamilyOf` даёт родного провайдера: начальный `models/` (длинная форма id Gemini) отбрасывается, затем id `local:` - `Local` (один маршрут, без ключа; картиночный вызов уходит в `LocalAgentProvider::GenerateImage`, который рисует для `local:codex-image` и падает с сообщением для остальных), id со слэшем (`vendor/model`) - OpenRouter, `gpt-…`, `o<цифра>…`, `chatgpt-…` и `dall-e…` - OpenAI, любой другой id - Gemini. `RoutesFor` перечисляет маршруты в порядке перебора: родной и иногда альтернативный с переписанным id: `gemini-X` - OpenRouter `google/gemini-X`; текстовые id OpenAI и `gpt-image-X` - OpenRouter `openai/<id>`; `google/gemini-X` и `google/gemma-X` - Gemini `gemini-X` / `gemma-X`; `openai/<id>` - OpenAI `<id>`. Альтернативы нет у `imagen-…`, `dall-e-…`, составных id `openai/…` с `-image`, кроме `openai/gpt-image-…` (`openai/gpt-5-image`), id с суффиксом варианта `:`, алиасов Gemini `-latest` и у остальных вендоров. `ChooseRoute` берёт первый маршрут, для которого задан ключ, и пишет в лог выбор не родного маршрута. `Plan` решает, где идёт вызов: локальный агент - здесь; маршрут с ключом этого редактора - напрямую (`route: own key (<провайдер>)` в логе); без ключа, когда проект подключён к AssetsLine, - через `AssetsLineAi`; ни того ни другого - нода падает с `NoKeyMessage`. `AssetsLineAi` отправляет вызов в `/api/sync/ai/{text,image,video,speech,sfx,music}` с токеном, проектом и id клиента синхронизации, именем пайплайна и нодой, никогда с ключом: AssetsLine выполняет его по своей маршрутизации и тарифицирует подключённый аккаунт и проект (его токены или сохранённые там ключи); в лог пишется `route: AssetsLine - <маршрут> (<потрачено> tokens, <остаток> left)` из заголовков `X-AssetsLine-*`, а ответ с ошибкой становится сообщением ноды (402 `Out of AssetsLine tokens` со ссылкой на пополнение, 403 - маршрут или роль запрещены, 422 - отказ, 502 - ошибка провайдера). Ключ, вызов на котором упал, никогда не уходит в AssetsLine - это тратило бы его токены без спроса. Ноды видео, речи, звуковых эффектов и музыки выбирают так же через `PlanDirect` по ключу своего провайдера. Неудачный вызов на другом маршруте не повторяется. Ключи берутся из `Editor::PipelineSettings` (`Work/Pipelines/PipelineSettings.json`). Запросы идут через `o2Network.RequestAsync`, повторы сообщаются событиями `Retry`. Тесты `LocalAgent.*` (`o2EditorTests`): маршруты, меню, вызов и его разбор, поддельный скрипт `claude` целиком, локальная команда; `LocalAgent.RealClaudeCodeAgainstAStubApi` запускает установленный Claude Code против заглушки Anthropic API (`O2_LOCAL_AGENT_STUB_URL`, на неё направляется `ANTHROPIC_BASE_URL`) - токены не тратятся. ## Выполнение

`Editor::PipelineExecutor::Execute(pipelineId, graph, targetNodeId, dirtyNodeIds, cachedOnly)` выполняет цепочку выше целевой ноды в порядке зависимостей. Результаты кешируются в `Work/Pipelines/cache/<pipelineId>/{content,previews,ran}` по сигнатуре ноды: нода с совпавшей сигнатурой берётся с диска, `cachedOnly` берёт ноды провайдеров из кеша или, если его нет, из последнего отрисованного превью (без отметки о запуске) и отказывает только нодам без того и другого (`Not cached`). `ResolveSourceValue(node, assetsPath, value, error)` (`Nodes/PipelineNodesCommon.h`) - единственное место, где нода-источник превращает конфиг в значение: через него работают сами источники, и им же редактор даёт источникам значение без запуска. `PipelineUtils::PrettyModelName(id)` переводит id моделей в названия для списков моделей; `PipelineModelMenu` (`Pipeline/PipelineModelMenu.h`) держит правила меню моделей, общие с `shared/modelMenu.ts` AssetsLine (группа id, порядок и сворачивание групп, поиск по полям, Recent, строка своего id), а `PipelineModelPicker` (окно Pipeline) рисует его всплывающим окном `PipelineEditor`; `PipelineOptionPicker` - такое же окно без поиска для фиксированного выбора с иконками и подсказками (цель генератора промптов). `PipelineGraph::GetRunTargets()` возвращает цели запуска всего графа: все ноды без исходящих связей, финишные первыми, без источников, которые никто не читает. Нода с `perPortRun` считается выход за выходом: производятся только порты, которые читает ветка (целевая нода считает все свои), каждый со своей сигнатурой (общий конфиг без `PortCacheExcludedKeys` плюс `PortCacheVariant`) и своим превью (`GetPortPreviewPath`, `LoadPortPreview`, событие `NodeOutput` с `portId`), поэтому упавшая или изменённая часть не трогает остальные; потребитель такого выхода хешируется по той части, которую читает (`PipelineGraph::ComputePortSignature`, `OutputSigKey`), так что две одинаково настроенные ноды на двух частях не делят ячейку кеша. Часть сигнатуры порта, отвечающую за прозрачность, даёт `PipelineTransparency::PortCacheSuffix`: часть без собственных настроек хешируется байт в байт как до их появления (при хромакее ноды её сырой рендер выбрасывает `chromaTolerance/Softness/Spill` и помечается `|chroma-raw`); часть с собственными настройками выбрасывает все шесть ключей ноды и добавляет после варианта части `|bg:[<transparentBg>,"<mode>","<ключевой цвет>"]` (ключевой цвет остаётся в ключе, как и у ноды), затем `|chroma-raw` для сырого рендера или `|cut:[tol,soft,spill]` для того, что уходит дальше по графу. Её допуск, мягкость и подавление ореола никогда не входят в ключ сырого рендера, поэтому их изменение перевырезает закешированный рендер; перевод части на собственные настройки меняет её ключ, и она устаревшая до следующего запуска. Исполнитель вырезает каждую часть по её действующим настройкам. `ExecuteSingle` выполняет одну ноду, `Cancel()` останавливает после текущей, `assetsPathOverride` перенаправляет финишные ноды (тесты). События (`Editor::PipelineExecEvent`): `NodeState` (`queued`, `running`, `done`, `error`; с `portId` - про одну часть ноды с попортовым запуском: `running`, когда часть действительно начинает считаться, но не при попадании в кеш, затем `done` или `error` с сообщением, всё между `running` и `done` самой ноды), `NodeOutput` (`Editor::PipelineValue` с `previewPath`/`srcPreviewPath`), `Retry`, `Log`, `Done`, `Fatal`. `LoadPreview` и `ClearNodeCache` управляют кешем из редактора. `PipelineNodeWidget::SetParamsOpen` сразу показывает или прячет список параметров карточки (`paramsOpen`, UI-ключ) и у карточки с заданной высотой ставит `size.y = max(minHeight, shown + autoAfter - autoBefore)`, записывая это как изменение размера; `KeepAreaThrough(change)` делает то же для любого изменения содержимого (`PipelineNodeBody::RebuildBodyKeepingArea` для переключателя прозрачного фона, способа, модели, частей вырезания), без привязки к сетке; растягивание держит высоту не меньше `GetAutoHeightForWidth` той ширины, на которой оно закончилось. Холст рисует связи под карточками, затем карточки, затем связи, выходящие из порта, который тело ставит внутри карточки (`PipelineNodeWidget::IsBodyPort`, части ноды вырезания), с теми же цветами и выделением, затем маркеры портов; выбор связи от порядка не зависит. Редактор хранит состояния частей в `PipelineNodeRuntime::portStates` и сбрасывает их, как только нода перестаёт выполняться или стоять в очереди; `PipelineNodeWidget::ApplyRuntime` передаёт каждое изменение состояния телу (`PipelineNodeBody::OnRunStateChanged`), и карточка вырезания обновляет ячейки на месте.

Финишные ноды пишут результат в `<assets>/<assetPath>.<ext>` (при необходимости обрезанный и масштабированный; `keepAspect` вписывает картинку в `resizeW`x`resizeH`, а не растягивает её) и ставят `assetsChanged`; в редакторе исполнитель затем вызывает `o2Assets.RebuildAssets()`, а с `deferAssetsRebuild` (окно Pipeline) сообщает об этом в `Done` и оставляет пересборку окну (см. Фоновая работа и статус).

`Editor::PipelineValue` — `type`, `data` (текст или закодированные байты), `mimeType`; конструкторы `Text`, `Image(bitmap)`, `ImageBytes`, `Bytes`, `GetBitmap()`; `DecodeImageBytes` декодирует PNG, WebP (декодер libwebp 1.4.0, вложен в `Framework/3rdPartyLibs/libwebp` и подключён только к редактору - некоторые модели OpenRouter отвечают WebP), JPEG, BMP и GIF; `ToPngBytes` перекодирует любой из них в PNG, `GetPngBytes` решает по байтам, а не по метке. `Editor::PipelineUtils` — рабочие пути (`SetWorkPathOverride`), загрузки, data URL, base64, FNV-хеши, hex-цвета, чтение и запись файлов.

`PipelinePairLayout` (`Pipeline/PipelinePairLayout.h`) держит правила «вход | результат», общие с `extractPair` / `cellCorner` AssetsLine: какие типы нод показывают вход рядом с результатом (`IsPairNode`, `InputPortOf`), ширину панелей и высоту строки, сетку вырезания (`ExtractGrid(rowWidth, parts, rowHeight)`: естественная строка вмещает колонки не уже 64 и не ниже 176, карточка с заданной высотой делает её выше; в строке одна часть занимает всю панель, несколько — квадратные ячейки в том числе колонок, при котором они крупнее всего, сетка по центру (`offX`, `offY`), подписи высотой 20 под ячейками; `ExtractCellCorner` даёт положение порта - правый верхний угол картинки ячейки; кнопки перегенерации / удаления ячейки стоят слева сверху, а этот угол вырезан из области клика ячейки), высоту 0 как «автоматическую» (`IsAutoHeight`, `NewNodeSize`, `HeightAfterResize`), `ShowsCompare`, локальную настройку вида (`GetIoView/SetIoView`, `Work/Pipelines/ViewPrefs.json`, версия, по которой открытые редакторы пересобирают такие карточки) и разделитель каждой ноды. В окне `PipelineNodeBody::AddPairRow` добавляет `PipelineIoPair` (панель входа, виджет результата, `PipelineCompareView`); тела image edit и extract ставят результат или сетку частей рядом со сценой рисования (`PipelinePaintEditor::SetBeside`, `SetCompare` для разделённой сцены), а тело вырезания ставит порт каждой части через `GetRowPlacement` + `ExtractCellCorner` (`HasBodyPort`, `GetBodyPortOffset`). `PipelinePairDraw` рисует обрезанные картинки, разделитель в один экранный пиксель и ручку экранного размера (`BadgeScale` = min(размер пикселя, 1.5), `GripRect`).

Тело может само нести входные порты: `PipelineNodeBody::InputsInBody` убирает их из строк портов (вместе со строкой добавления входа), `GetBodyPortOffset` ставит каждый на левый край карточки, а `IsAddInputAt` - строка добавления входа в теле; так делает композер через `PipelineComposerLayersPanel` (`PipelineComposerLayers.h`), чьи закреплённые высоты строк дают положения портов без измерений; `GetAddInputPlace` сообщает, на какой строке добавления стоит точка. `PipelineComposerLayout` (`Pipeline/PipelineComposerLayout.h`) держит правила композера, общие с `shared/composer.ts` / `composerLayout.ts` AssetsLine: строки списка (`Rows`: `+ layer on top`, строки слоёв с раскрытыми настройками, `+ layer below`), размер экспорта слоя (`LayerExportSize`, `HasExportSize`, `TypeExportSide`; `exportW` / `exportH` в `config.layers[id]`, сохраняются при чтении и записи слоя), место нового слоя (`OrderWithNewLayer`, `PlaceNewLayer`: `layerOrder` и `selectedLayer`, их пишут `PipelineEditor::AddCustomInput` и связь, брошенная на строку добавления, в том же шаге отмены, что вход и связь) и `FrameScale` = clamp(1 / масштаб камеры, 0.5, 4), по которому задаются размеры `PipelineComposerFrame` (движковый `FrameHandles` с рукоятками экранного размера) и плашки размера.

`PipelineUpscale` (`Pipeline/PipelineUpscale.h`) держит правила AI-апскейла из `shared/upscale.ts` AssetsLine: `Target` (×2/×3/×4 или размер с замком пропорций, не больше 8192), `ClosestAspect` среди кадров, которые рисует модель, `RenderSizeFor` (1K / 2K / 4K), `RendersLargeSizes` (модели Gemini 3 для картинок, напрямую или через OpenRouter) и промпт. Запрос картинки принимает `AiImageOptions` (разрешение и кадр): Gemini кладёт их в `generationConfig.imageConfig` (`GeminiProvider::BuildImageBody`), чат OpenRouter - в `image_config`, OpenAI выбирает ближайший из трёх своих размеров (`OpenAiProvider::SizeFor`).

`PipelineEditRegion` (`Pipeline/PipelineEditRegion.h`) - рамка ноды правки картинки, по тем же правилам, что `editRegionOf` / `regionBoxes` / `pasteRegionEdit` AssetsLine: `Read` проверяет значение `editRegion`, `Of(node)` читает его у ноды правки, `PixelBoxes` даёт рамку в пикселях и контекстную область, `Weight` - вес смешивания пикселя области, `PasteRegionEdit` вмешивает ответ модели обратно. `PipelineTransparency::Read` сообщает об отсутствии прозрачности у ноды правки с рамкой, поэтому за ним следуют хромакей, запрос прозрачности у модели и `ImageGenerations`. В окне `PipelinePaintEditor::Init(node, withRegion, regionKey, optionalRegion)` хранит рамку под ключом: `roi` у исходника вырезания, необязательный `editRegion` у сцены правки, который создаёт инструмент рамки и убирает её кнопка удаления; `SetDrawingEnabled(false)` (вырезание) убирает панель инструментов и слой рисунка и оставляет рамки редактируемыми, а вырезание переносит рамку выбранной части в `roi`, если пайплайн, сохранённый в другом месте, оставил его рассогласованным. `AiRouter::SetImageStub` отправляет все запросы картинок в функцию вместо провайдера (тесты).

Все точки входа, из которых карточки могут строить виджеты между кадрами (`PipelineEditor::Update`, `OnExecutorEvent`, `PipelineNodeWidget::OnOutputChanged/OnConfigChanged/ApplyRuntime`, `PipelineNodeBody::RebuildBody`, панель слоёв композера), выставляют `PushEditorScopeOnStack`: виджет, созданный вне editor-scope, регистрируется как объект сцены - это засоряло сцену и роняло её при пересборке карточки.

События исполнителя приходят в редактор в главном потоке: корутины исполнителя продолжаются на воркерах (`co_await` запускает дочернюю на `JobThread::Any`), поэтому `onEvent` у `PipelineEditor` передаёт каждое событие задаче главного потока (копию без кэша декодированной картинки, потому что счётчики `o2::Ref` не атомарны), и `OnExecutorEvent` выполняется там.

## Фоновая работа и статус

Окно оставляет главный поток интерфейсу: то, что занимает время, выполняется на воркерах или распределяется по кадрам и показывается, пока идёт.

- **Картинки.** Значение-картинка хранит декодированный растр в слоте, общем для его копий (`PipelineValue::decoded`, `ShareDecoded`, `PeekBitmap`); редактор даёт слот каждому значению, которое хранит (`LoadPreview`, `OnExecutorEvent`, `RefreshSourceOutput`), так что картинка декодируется один раз, сколько бы карточек её ни показывали. Карточки просят её через `PipelineNodeBody::Picture` → `PipelineEditor::GetPicture`: ещё не декодированную `PipelineImageLoader` декодирует на воркере вместе с копией не больше 1024 px, карточка тем временем показывает `loading..`, а `ApplyDecodedPictures` между кадрами в пределах 6 мс отдаёт результаты и вызывает `OnOutputChanged` у карточек, которые просили. `PipelineDisplayCache` держит одну текстуру размера карточки на растр для всех видов (картинки, пары и сравнения, сцена рисования, слои композера). Картинки источников для карточек читаются без декодирования (`ResolveSourceValue(..., decodeImage = false)`). Холст рисования (image edit, paint), чья картинка ещё декодируется, тем временем не раскладывается (`PipelinePaintEditor::SetBackground(bitmap, pending)`): сохранённый рисунок загружается один раз, в размере картинки. Карточки аудио и видео делят один `SoundAsset` на клип, так как ассет остаётся в кэше ассетов до конца сессии.
- **Запуски.** `ExecuteWork` / `ExecuteSingleWork` (входы, нода, её превью, запись кэша, сигнатуры) выполняются на воркере; в главный поток возвращается только `FinishRun`. Редактор включает `deferAssetsRebuild`: `Done` запуска несёт `assetsChanged`, и ассеты пересобираются один раз, после последнего запуска в очереди, в фоне (`Assets::RebuildAssetsInBackground`); сохранение ассета (`IAssetEditorWindow::SaveEditingAsset`) и сохранение слоёв композера пересобирают так же. Превью видео читают атлас кадров в своём потоке.
- **Карточки.** Undo, redo, перезагрузка, удаление и вставка меняют только свои карточки (`SyncGraphTo`, `AddCard`, `RemoveCard`); переименованный слой композера и переименованная часть extract оставляют карточку и её строки. Карточки вне вида после открытия раскладываются по несколько за кадр (`WarmUpCards`, 2 мс за кадр). Сдвинутая камера пишется в документ ассета через 0.25 с после остановки. Связи кадра собираются один раз для обоих проходов (`CollectEdgeDraws`).
- **Статус.** `PipelineEditor::GetBackgroundStatus()` (`Loading previews 12/150`, `Applying Outline`, `Rebuilding assets`) показывается в панели окна; карточка, занятая фоновой работой (`PipelineNodeWidget::IsBusyInBackground`: применяется её эффект, декодируются её картинки), рисует тонкую бегущую полоску под заголовком.

`PipelinePerfUiFixture.*` в `o2EditorUITests` замеряет основные действия на больших пайплайнах проекта (`O2_PIPELINE_PERF=1` или папка проекта, результаты JSON в `O2_PIPELINE_PERF_OUT`); `PipelineResponsivenessUiFixture.*` держит поведение выше.

## Группы нод, выведенные ноды, входы

Меню добавления нод (правый клик, связь, брошенная на холст) показывают шесть групп AssetsLine (`PipelineNodeGroups`: Input & output, AI images, Image tools, Text, Game UI, Audio & video), каждая — подменю со счётчиком (`ContextMenu::Item::hint`); брошенная связь предлагает совместимые ноды, тоже по группам. Схема с `retired` (Remove background (two-pass), Text compose) нигде не предлагается, но загружается и работает. Значения входов, добавленных через «+ input», читаются по id порта (`PipelineNodeBase::InputOf`, в промпте их называет `InputLabel`: `input 1`, `notes 2`): безымянные и одноимённые входы больше не затирают друг друга.

Схема с `partialInputs` (UI kit, AI UI layout) запускается с теми входами, у которых есть результат; `PipelineNodeRegistry::IsReferenceInput` (все входы Text style, все входы AI UI layout кроме kit) отмечает входы, которые читает только ИИ ноды: `PipelineGraph::GetRunInputEdges` исключает их из запусков, сигнатур и автоприменения.

## Плотность пикселей

`PipelinePngMeta` (порт `shared/pngMeta.ts`) читает и пишет метки AssetsLine в PNG: tEXt-чанки `AssetsLine:dpi` / `AssetsLine:scale` и чанк pHYs, байты совпадают с вебом. Часть AI extract помечается тем, во сколько раз модель нарисовала её крупнее кропа (`PipelineRegions::PartScale`, хранится с генерацией), и после каждого запуска `DPI = DPI источника x масштаб` (`TagExtractPart`; DPI источника = `sourceDpi` ноды, иначе метка входа, иначе 480): `sourceDpi` не входит в ключ сохранённой генерации, но входит в то, что хешируют потребители. Image crop сохраняет метку (при изменении размера масштабирует её); картинка-источник сохраняет свои байты PNG. UI kit берёт DPI элемента из его настроек, иначе из метки входа.

Порт AssetsLine `shared/uiDoc/rotate.ts` (`UiDoc/UiDocRotate.*`). `UiNode::rotation` (градусы по часовой стрелке на экране; `CleanTurn`: (-180, 180] с точностью до десятой градуса, 0 — нет поворота) стоит в `NodeKeys` после `grow`, читается из `rot` / `angle` / `rotate` (модель и UIML) и никогда не ставится корню. Раскладка решается так, будто ничего не повёрнуто; `WorldMatrix` (повороты блока и его родителей вокруг центров их рамок), `WorldTurn`, `Corners`, `InBlock` и `HitTest` (он снимает повороты по пути вниз) дают, где всё находится на экране. `TurnedBounds` / `UnturnedSize` — математика черновика для наклонённого элемента.
- **Рисование**: `Render::Renderer::Node` рисует повёрнутый блок с детьми без поворота на своём слое, центр блока в середине слоя (так блок, частично ушедший за экран, сохраняет всю картинку), и кладёт слой повёрнутым (`UiCanvas::CompositeTurned`, билинейно) — как веб `<g transform="rotate(θ cx cy)">`; прозрачность идёт вместе с ним.
- **Сцена** (`UiWsStageTurn.cpp` и повёрнутые части `UiWsStage.cpp` / `UiWsStageDraw.cpp`): выделение, его родитель, наведение, призрак и треугольники якоря рисуются повёрнутыми (`BlockMatrix`, `TurnedFrame`, `AnchorTriangles`), ручки на повёрнутой рамке (`HandlePoint`), курсоры следуют повороту (`HandleCursor`), ручка поворота над верхним краем (`KnobPoints`, захват `turn`, `DragKind::Rotate`: Shift — шаги по 15°, прилипает к 0 / 90 / 180 в пределах 4°); повёрнутый блок (или блок в повёрнутом родителе) захватывается по `InBlock`, двигается вдоль осей родителя и меняет размер вдоль своих без прилипания, а изменение размера сдвигает рамку на (R − I)(c' − c). Инспектор: строка Rotation (поле °, `turn:left` / `turn:right`).
- **Агент**: строка спецификации UIML (`UiUimlSpec`), правило разметки для наклонённых элементов (`MarkupFlatRule`), `parse` оставляет наклон от 2°, черновик поворачивает блок и уменьшает его рамку до размера без поворота, `UiLayout::KeepTurns` возвращает повороты черновика после прохода скилла.
- **Экспорт**: `ui_structure.json` несёт `rotation` (`ToUiStructure`, `FromUiStructure` его читает); прототип o2 (`UiLayout::PlanWidgets` / `BuildWidgets`) ставит виджету пивот (0.5, 0.5) и `angleDegrees` = −θ (o2 поворачивает вокруг пивота, y вверх; дети поворачиваются вместе с ним) — экспорт o2 в вебе только предупреждает.
- Тесты: `UiDocRotation.*` (веб `uiRotation.test.ts`, проверки SVG — как проверки пикселей, поворот виджета o2), golden `UiDocGolden5.*` (`UiDocGolden/cases5.mts`: cleanTurn, математика, проверки попадания по сетке, правки, структура, keepTurns, правило разметки); UI `UiWorkspaceTurnFixture.*` (ручка поворота, блок в повёрнутом родителе, изменение размера повёрнутого блока, строка Rotation).

## Второй шаг: проверки по референсу

**Шаг уточнения.** У ноды может быть платный второй шаг над сохранённой генерацией порта: `IPipelineNodeImpl::RefineKey(node, portId)` (пусто, пока шаг выключен), `Refine(ctx, inputs, node, stored, key)` -> `PipelineRefineResult {value, keep}` и `RefineReplayed(ctx, node, key)`. `PipelineExecutor::RefineStored` (`PipelineExecutorRefine.cpp`) запускает его после того, как генерация сохранена или прочитана из кеша, — для каждой части per-port ноды и для ноды с одним выходом (картинка или стиль текста: его JSON считается его байтами; прочий текст не уточняется) — и до вырезания chroma, `PostStep` и кропа. Результат кешируется под `RefineSignature(cacheSig, key, stored)` = первые 32 hex-цифры sha256(`<cacheSig>|<key>|` + байты генерации), так что восстановленная или перегенерированная генерация проверяется заново; `keep: false` (вызов модели упал) ничего не сохраняет, следующий прогон пробует снова; ↻ удаляет его вместе с генерацией. Попадание в кеш пишет в лог `check cache hit` и вызывает `RefineReplayed` (debug-файл следует за сохранённой проверкой). Прогон только из кеша за него никогда не платит: где шаг ещё не выполнялся, сохранённая генерация остаётся как есть, лог пишет `check not run yet`, и нода не отмечается выполненной (`refineOwed`). Контекст несёт часть (`outputPortId` / `outputPort`), `workDir`, `fresh`, мемо (`PipelineExecutor::AttachWork`, общий с нодами динамических выходов; `ctx->MemoGet` / `MemoPut`) и `phase`: `ctx->Phase("check" | "redo")` шлёт `NodeState running` с `PipelineExecEvent::phase` для части (или ноды), редактор хранит его в `PipelineNodeRuntime::phases`, пока часть не остановится. В o2 нет дублей (takes), поэтому веб-правилу «оставленная попытка — отдельный дубль» соответствия нет.

**AI extract: проверка по референсу** (`PipelineExtractCheck`, `PipelineExtractCheck.cpp` + `PipelineExtractCheckRun.cpp`, порт `backend/src/nodes/extractCheck.ts`). Конфиг `refCheck` (выкл.), `refCheckMax` 1/2/3 (2), `refCheckModel` (`gpt-6.1-sol`): `PipelineExtractCheck::Read`; ключ уточнения `ref-check:v1:<model>:<limit>`. Ключи не входят в ключ генерации части и, пока выключены, в сигнатуру ноды (`PipelineGraph::IsRefCheckOn`). На каждую попытку: спрайт сохранённой генерации (`SpriteViewOf`: chroma-часть режется так же, как пост-шаг, любая другая хранится обрезанной с кадром в tEXt `AssetsLine:frame` = `frameW,frameH,left,top`, который `PipelineExtract::GeneratePart` пишет только при включённой проверке, `ReadPngFrame`; без него спрайт ставится по центру), положенный на свой кроп (`PlaceOnCrop`: измеренный размер из `PipelinePartFit`, грубый сдвиг, затем `UiLayout::Register`), поверх референса = региона с четвертью его стороны вокруг (`RegionRect`, `ContextRect`, `OverlayOn`: пиксельная разница и доля изменённых); судья получает референс, наложение и спрайт на шахматке (`SpriteOnChecker`) в масштабе 384..1024 px с `JudgePrompt` и отвечает `{verdict, likeness, differences, instructions}` (`ParseJudge`); `significant` перерисовывает часть с `ClarificationsOf` в промпте (`GeneratePart(..., extra)`), до лимита; `BestAttempt` оставляет сначала принятые попытки, затем по похожести. Ответы судьи и рисования мемоизируются (`ShaKey`: `extract-check-judge:v1` / `extract-check-draw:v1` + что спросили); непрозрачная часть и подложка пропускаются. Debug-данные: `<work>/check/<part>.json` (и `<part>-<key8>.json`, картинки референса, спрайта и наложения; `running: true`, пока идёт; хранятся три последние проверки части, файлы исчезнувших частей удаляются).

**AI text style: проверка по картинке** (`UiDoc/UiStyleCheck.*`, порт `backend/src/uiKit/styleCheck.ts`): те же три ключа, ключ уточнения `style-check:v2:<model>:<limit>` (повышать при изменении промпта судьи). Слова надписи рисуются в стиле рендерером раскладки на цвете края самой картинки (`StyleBackdropOf`; серая подложка для прозрачной картинки) шириной не больше 1024 px (`RenderStyleSample`, `SampleDoc`); судья получает картинку так, как её видела модель стиля (`StyleSourcePicture` с `srcCrop`), и образец с `StyleJudgePrompt` (стиль, который он может менять, прежние попытки, каталог шрифтов, `StyleLookSpec`); его поля `style` накладываются на попытку (`ApplyJudgeFix`: никогда размер, имя и роль), `StyleChanges` перечисляет изменения, остаётся лучшая по похожести попытка с именем, ролью и `extracted` прочтения. Debug-данные: `<work>/check/style.json`.

**Карточки.** `PipelineCheckRows::Add` кладёт в список параметров разделитель, переключатель и, пока он включён, сегменты лимита и строку модели судьи; `PipelineCheckDlg` — окно подробностей (попытки рядом, строка итога, просмотр 1:1; следит за debug-файлом, пока тот меняется). Тесты: `PipelineExtractCheck.*` (14, веб-тесты `extractCheck.test.ts` с заглушками моделей картинок и зрения), `PipelineStyleCheck.*` (часть `textStyleFx.test.ts` про проверку, фон, исправление, пути «только из кеша» и ↻) в `o2EditorTests`; `PipelineChecksFixture` в `o2EditorUITests`.

## AI image to UI

Выведена с 2026-11-12 (`schema.retired`): AI UI layout делает это с UI-китом; ноды в существующих пайплайнах загружаются и работают.

`imageToUi` (`Pipeline/Nodes/ImageToUiNode.*`, ядро в `Pipeline/UiLayout/`, пространство имён `Editor::UiLayout`) работает как [XuToWei/Image-To-UI](https://github.com/XuToWei/Image-To-UI): его скилл запускается **без изменений** (Python), а модель зрения выступает агентом, для которого скилл написан. Нода делает то, что скилл считает данным, - папку нарезанных спрайтов, вырезанных из макета, - отвечает на вызовы модели агента и превращает папку задачи скилла в выходы. Это порт `backend/src/uiLayout/run.ts` AssetsLine, контракт хоста - `o2/Tools/ImageToUi/PORTING.md`. `PipelineImageToUi` (`Pipeline/PipelineImageToUi.h`) держит то, о чём договорились три редактора (`shared/imageToUi.ts` AssetsLine): значения по умолчанию, `ReadConfig` (`maxTurns` 4..120, карточка предлагает `TurnOptions` 20 / 40 / 60 / 90 / 120, по умолчанию 60), `SpriteName` (`preview` / `layout` становятся `sprite_<key>`), `SpritePorts`, `SummarizeLayout` (спрайты - различные `asset`), `ReadRunSummary` (`summary` трейса), `RunLine`, `SummaryLine`, а также правила правок после запуска (ниже).

**Выходы, которые решает запуск.** Схема с `dynamicOutputs` запускается один раз на все выходы (`PipelineRunResult::outputs` по имени, `order` - порядок запуска) в `PipelineExecutor::EvaluateDynamic` (`PipelineExecutorDynamic.cpp`). Результат - пакет под сигнатурой ноды: `content/<sig>-outputs.json` = `{"outputs":[{name,type,key,ext}]}` и по файлу на выход под `BundleKey(sig, name)` = первые 32 hex-цифры sha256(`<sig>#<name>`); загрузка без любого из файлов - промах, на пайплайн и сигнатуру идёт одно вычисление за раз, обход (↻) удаляет пакет и выставляет `ctx->fresh`, `cachedOnly` сообщает `Not cached`. `DynamicPorts` даёт порты: сначала выходы схемы, затем остальные в порядке запуска; выход, который у ноды уже есть, сохраняет id порта, новый получает id схемы или `sp-<name>` (символы вне `[A-Za-z0-9_-]` - `_`). Исполнитель шлёт `NodePorts`; `PipelineEditor::ApplyNodePorts` даёт живой ноде эти выходы, убирает связи ушедших портов, перестраивает карточку и сохраняет пайплайн без шага отмены. Первый выход - превью ноды, каждый остальной - превью порта (картинки `.png`, разметка `.txt`), устаревшие превью портов удаляются. Контекст несёт `workDir` (`Work/Pipelines/cache/<pipeline>/work/<node>/`, трейс), `fresh` и `memoGet` / `memoPut` (ответы моделей, запомненные в папке контента под ключами `uil-t-` / `uil-i-`: первые 40 hex-цифр sha256 по частям, каждая с NUL в конце). Ключ кэша потребителя динамического выхода - `PipelineGraph::DynamicPortSignature(sig, port)`, так что два выхода никогда не делят слот. Синхронизация отправляет выходы 1..n частями `<node>#<port>` с расширением по типу порта и засевает скачанный результат как пакет (`AssetsLineSyncResults::SeedBundle`), так что запуск, сделанный в вебе, экспортируется здесь без повторных вопросов моделям.

**Python** лежит в `o2/Tools/ImageToUi/`: `upstream/` (скилл, не правится), `agent/agent.py` (окружение агента) и `PORTING.md`, их копирует из `AssetsLine/image-to-ui/` скрипт `tools/sync-image-to-ui.sh` (o2-Template). `ImageToUiHome` находит его от корня проекта или вверх от рабочей папки (`O2_IMAGE_TO_UI_DIR` переопределяет). Интерпретатор - настройка пайплайна `imageToUiPython` (`Python 3` в диалоге AssetsLine); пустая - `FindPython` берёт первый из `python3` в `PATH`, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, который импортирует Pillow и numpy (проба кэшируется по `PATH`), иначе первый найденный - тогда агент выходит с кодом 3 и его `detail` (что поставить) становится ошибкой ноды.

**Запуск** (`UiLayoutRun.cpp`): анализ (`Prompts::Analyze`, `ParseAnalysis`: id, сетки развёрнуты в ячейки с их текстами; `AnalysisFrameOf(model, w, h)`: модель Gemini отвечает `box_2d` на сетке 0..1000, любая другая получает дизайн, уменьшенный до 1568 px / 1.15 Мп максимум, и отвечает `box` в пикселях этой картинки, пересчитанных назад `BoxFromPixels`, - другие модели плывут на сетке 0..1000; затем `FitGrids` (`UiLayoutGridFit`) ставит каждую сетку на ячейки, которые показывает картинка: шаг - период её перепадов, границы ячеек идут по зазорам, пустой столбец или ряд, добавленный моделью, убирается, рамка на ряд короче получает шаг картинки, и подгонка остаётся, только если её линии спокойнее линий модели; шаг пишет, что сдвинулось, и хранит рамки как ответила модель рядом с подогнанными), замер текстов по чернилам (`UiLayoutMeasure`; только для того, что нарезка должна стереть), `PlanLooks` и нарезка (`CutAll`, по четыре сразу, у каждого воркера свой `ParallelAiCtx`; `UiLayoutSlice`, `UiLayoutMatte`: кроп, цвет ключа, рендер моделью, хромакей, совмещение, деформация, despill, композит, заливка остатков, поля nine-slice для панелей; плохая матте режется ещё раз с другим сидом), фон (`MakeBackground`: цвет или подложка, проверенная `PlateLeftovers`, запрошенная ещё раз и залитая `HarmonicFill`). Затем входы скилла в `<workDir>`: `input/design.png` (сведённый на белый) с тремя файлами Roboto рядом, плоская `sprites/<name>.png` (`AssetFileName`: ключ вида в безопасном виде плюс `panel_` / `button_` / `bar_` / `icon_`, если ключ этого не говорит; повторы `_2`), `<name>.png.meta` со вспомогательным `spriteBorder` скилла для видов с nine-slice (`NineSliceMeta`), `sprites/bg_backdrop.png` для подложки, `fonts/Roboto-*.ttf` + `LICENSE-Roboto.txt`, свежие `task/` и `agent-view/` (сохранённые состояния прежних правок - `rounds/`, `edits/`, `rounds.json` - тоже удаляются). Трейс сбрасывается на диск, агент работает, трейс перечитывается (агент дописал свои шаги), и выходы - `task/reconstruction.png` (`preview`), `task/ui_structure.json` байт в байт (`layout`) и по картинке на каждый спрайт, который называет разметка (`AssetRefs`: каждый `asset`, со состояниями), в порядке первого упоминания в разметке (имя без файла в `sprites/` пропускается; поля nine-slice - из его `.png.meta`). Результат с `ok: false` роняет ноду (`the agent ended without a checked layout (<error или status>)`); незавершённый запуск всё равно отдаёт выходы, лог и трейс говорят NOT completed с блокерами. Шаги пишутся в `<workDir>/trace/trace.json` с картинками по ходу дела (`Trace`).

**Правки после запуска** (`UiLayoutRounds.cpp`, порт `runLocked` / `Rounds` из `run.ts`; контракт хоста - раздел 6 `PORTING.md`). Конфиг `edits` - раунды по порядку, `[{id, items: [{text, at?: {on: "design" | "result", x, y}}]}]`; `PipelineImageToUi::Edits` / `EditItems` чистят его как `shared/imageToUi.ts` (текст обрезан по краям и до 2000 единиц UTF-16, пустые заметки и раунды выброшены, не больше 20 заметок, `on` - `result`, если не `design`, x / y округлены и не меньше 0, без id - `e<n>`), `EditTurns(maxTurns)` = max(12, round(maxTurns / 2)) ходов на раунд. `edits` входит в сигнатуру (результат каждого раунда кэшируется отдельно), `editsDraft` (неотправленные заметки) и `editsView` (диалог открыт) - ключи только для UI. `RunImageToUi` держит рабочую папку для одного запуска за раз (`FolderHold`: раунд, добавленный пока идёт предыдущий, ждёт) и продолжает с сохранённых состояний: `rounds.json` = `{base, note, summary, rounds: [{id, hash, summary}]}` (`base` = `ImageToUiBaseKey`: sha256 по байтам входа и JSON из `model`, `imageModel`, `maxTurns`, `sprites`, `background`, `name`, `hint` и сида; `note` - заметка о спрайтах; `hash` = `ImageToUiRoundHash`, первые 16 hex-цифр sha256 по JSON заметок раунда), `rounds/<k>/` = `ui_structure.json`, `alignment_review.md`, `component_review.md` и `trace.json` состояния k (0 - запуск без правок). Стартовое состояние - самый длинный префикс `edits`, совпадающий с сохранёнными раундами (та же база, файлы состояния, дизайн и `sprites/` на месте); если такого нет, или ↻, выполняется всё (`RunBase`) и сохраняется состояние 0. При продолжении берётся трейс состояния (его закрывающий шаг `output` / `edit<n>-output` снимается, если дальше раундов нет), его файлы возвращаются в `task/` там, где отличаются, и если раундов дальше нет, а что-то изменилось, хост запускает `workflow.py check` ради свежей реконструкции - без вызова модели; папка задачи без `workflow_state.json` (или пропавшая целиком) сначала готовится заново: файлы модели откладываются, `task/` удаляется (prepare не берёт непустую папку без своего состояния), `prepare`, файлы возвращаются (агент в `--revise` делает то же, шаг трейса `edit<n>-prepare`). Каждый оставшийся раунд n пишет `edits/round-<n>.json` = `{round, items, earlier: [{round, items}]}` и запускает агента с `--max-turns <EditTurns> --revise <этот файл>` (он сохраняет подготовленную папку задачи, проверяет разметку как есть, пишет картинки `@request/` с нарисованными и увеличенными точками, приставляет к id шагов трейса и картинкам `edit<n>-`); `ok` false роняет ноду (`edit round n ended without a checked layout`), результат с `error` (вызов модели не удался: кончились кредиты, сбой) тоже роняет (`edit round n stopped — the model call failed: …`), и от раунда ничего не сохраняется; иначе сохраняется состояние n и пишется `rounds.json`. Закрывающий шаг - `edit<n>-output` (`Edit n · Done …`) после раундов, иначе `output`; `summary.edits` = число раундов, и `trace.json` состояния заканчивается им. Нода, запущенная до появления раундов (нет `rounds.json`, папка задачи `completed` / `checked` / `finalize_failed`, сделанная из того же сведённого дизайна), усыновляется как состояние 0, её заметка о спрайтах собирается из папки (файлы `.png.meta`, `bg_backdrop.png` или цвет фона из трейса). `PipelineImageToUi::StateTracePath` - трейс текущего состояния ноды, как ответ сервера на `trace.json?edits=<ids>`: `rounds/<k>/trace.json`, когда раунды `rounds.json` начинаются ровно с id из `edits` (их k), иначе живой `trace/trace.json`; его читают итог карточки и окно отладки (результат из кэша никогда не переписывает `trace/`), картинки всех состояний остаются в `trace/`.

**Агент** (`UiLayoutAgent.*`): `AgentProcess` запускает `<python> -B agent/agent.py --design … --assets … --output … --scratch … --skill upstream/image-to-ui --max-turns N --name=… --hint=… --sprites-note=… --font fonts/Roboto-Regular.ttf --font fonts/Roboto-Medium.ttf --font fonts/Roboto-Bold.ttf --trace-dir … [--revise <файл раунда>]` (`AgentArguments`, свободные тексты как `--key=value`) через `posix_spawn` в `<workDir>`, в своей группе процессов и с неблокирующими пайпами (только POSIX; на других платформах нода падает с `cannot run on this platform`). `RunAgent` опрашивает пайпы раз в кадр: строка stdout `@@bridge {"type":"model","id","tag","prompt","images"}` получает ответ в stdin `{"id","text"}` или `{"id","error"}` через `AiText` (тег `agent <tag>`, память по модели, промпту и байтам картинок, JPEG уходит как `image/jpeg`), `event` пишется в лог, `result` - последняя строка; stderr хранит последние 8000 байт для ошибки агента, остановившегося без результата. Отменённый запуск убивает группу процессов.

**Экспорт** (`UiLayoutExport.cpp`, `UiLayoutWidgets.cpp`, `UiLayoutResolve.cpp`, `ImageToUiExport`): после свежего запуска и по `Save to Assets` прототип собирается из `ui_structure.json` скилла и выходов-спрайтов (их поля nine-slice - из запуска или из `.png.meta` рабочей папки) и сохраняется как `ActorAsset` в `Assets/<assetPath>/<screenName>.proto` (существующий перезаписывается на месте: сохраняются его uid и id акторов по пути), с `<screenName>_Resources/Sprites/<name>.png`, `white.png` для ровных цветов, `Fonts/` со всеми встроенными UI-шрифтами надписей (`BundledFontOf`: `fontFamily`, называющий файл из `o2/Tools/UiFonts`, читается оттуда или из `ui/pipeline/fonts` редактора) и лицензией каждого семейства, `FontStyles/*.fntstyle` для надписей, нарисованных не одним цветом (`TextLookOf` -> `FontStyleOf`: `FontColorEffect` или `FontGradientEffect` с первым и последним цветом — по каждому глифу, строки снизу вверх, направление к ближайшей оси — затем `FontStrokeEffect` на каждую обводку и `FontShadowEffect` на каждую тень; свечение — тень без смещения, объём — тень без размытия; имя `stroke_<заливка>_<обводка>_<радиус>` для одной обводки, иначе `text_<хеш>`). Тень берёт покрытие глифа в своём цвете, какая бы заливка или обводка ни шла до неё. `PlanWidgets` читает структуру так, как её рисует скилл: `SnapshotStructure` применяет текущий вариант каждого блока состояний и подписи прогресса (`FormatProgress`), `ResolveStructure` - порт `layout.py` (раскладки row / column / grid с отступами, промежутками и распределением, `align` / `vAlign` / `offset`, `responsive`, смещения прокрутки), каждый бокс крепится к точке своего `anchor`, блок `responsive` становится якорями и отступами o2. ## Синхронизация с AssetsLine
`Editor::AssetsLineSync` (`o2/Editor/Sources/o2Editor/Pipeline/Sync`) держит ассеты пайплайнов одной папки и связанный проект AssetsLine в согласии; им владеет `EditorApplication` и вызывает `Update` каждый кадр, окно Pipeline даёт ему `isPipelineFileBusy` (у открытого ассета несохранённые правки), `onPipelineFileChanged` (перечитать открытый ассет), `onResultsChanged` (перечитать превью) и `confirmDeletes` (вопрос `AssetsLineDeleteDlg`) и само сохраняет синхронизируемый пайплайн через секунду после правки. Связь - `o2::AssetsLineConfig` в `o2Config.assetsLine` (`enabled`, `serverUrl`, `projectId`, `projectName`, `folder`, `writeFinishAssets`, `pollInterval`); токен и состояние синхронизации - у пользователя в `Work/Pipelines/sync/` (`credentials.json`, `state.json`, `base/<id>.json`).

`AssetsLineClient` отправляет запросы (`Authorization: Bearer`, `X-Project-Id`, `X-Sync-Client`) через `o2Network`. Подключение: `StartConnect` получает у сервера код и открывает страницу подтверждения, затем опрашивает, пока не придёт токен; `ConnectWithToken` проверяет токен, созданный вручную, через `/api/sync/me`.

Проход (`SyncPass`, корутина) читает `/api/sync/state`, затем:
- **документы** (`SyncDocuments`): сканирует папку (файл без id берёт UID из meta, скопированный файл получает новые id, источник-ассет получает id выгрузки по содержимому), сравнивает каждый пайплайн с его базой (последней версией, общей для обеих сторон, без камеры) и сохранённой ревизией: отправляет локальную правку с `baseRev` (сервер сливает её с правками, сделанными тем временем, если пришла база; слитый ответ записывается обратно, если файл не поменялся снова), забирает удалённую правку, переименовывает и удаляет с любой стороны; файлы, которые редактор держит несохранёнными, пропускаются. Пайплайн, чей файл здесь пропал, а на сервере ревизия базы, удаляется там без вопроса, только если он единственный такой в проходе, который не первый для связи (`RestartLink`: загрузка состояния, подключение, отключение, синхронизация выключена или нет подключения, смена сервера, проекта, папки ассетов или синхронизируемой папки; первый проход заканчивается обменом документами без офлайна); иначе спрашивает `confirmDeletes` (нет хука - пайплайны забираются обратно в том же проходе). Пока вопрос открыт, его id не трогаются; ответ использует следующий проход, дошедший до id, и только если файла по-прежнему нет и ревизия на сервере та же; если действие не удалось, ответ возвращается;
- **результаты** (`SyncResults`, когда сдвинулся счётчик результатов сервера или локальный файл): сопоставляет ключи результатов AssetsLine (`<node>`, `<node>.src`, `<node>#<port>`, `<node>.raw` / `<node>#<port>.raw` - сырой рендер chroma-ноды или части, чьи действующие настройки - хромакей, `<node>.trace` - шаги отладки AI image to UI, её папка `trace/` одним zip (`ZipTrace` / `UnzipTrace`, версия по `trace.json`, подменяется целиком), отправляется только для ноды, актуальной здесь, обрабатывается раньше остальных ключей и никогда не задерживает ноду - сервер, который её отклонил, не спрашивают снова до следующего запуска) с файлами превью и контента в `Work/Pipelines/cache/<id>/`, выгружает изменённое здесь и скачивает изменённое там (изменено с обеих сторон - побеждает актуальный), обменивается выгрузками источников, помечает актуальным на другой стороне то, что актуально на этой - нода, актуальная на сервере, получает скачанное в кэш контента под ключом, по которому его ищет локальный запуск (`PipelineExecutor::ContentSignature`); перегенерированная с любой стороны нода сохраняет сигнатуру, поэтому пришедший результат заменяет хранимую генерацию, а отправленный отсюда снова помечается актуальным, чтобы сервер сделал то же самое, - и пишет результаты финишных нод в ассеты (скачанные или посчитанные запуском финишной ноды только из кэша). Картинка под ключом `.png` всегда хранится как PNG: скачанная в другом формате перекодируется, а файл, оставленный прежней версией как WebP под именем `.png`, переводится в PNG на месте в начале `SyncResults` и остаётся синхронизированным (известная отметка файла обновляется, ничего не выгружается).

Тесты: `PipelineFormat.*` (формат, seed, круговая запись документов AssetsLine, найденных на машине), `AssetsLineSync_.*` (сквозные против настоящего сервера: задать `O2_ASSETSLINE_TEST_URL`, одноразовый поднимается `AssetsLine/backend/scripts/test-instance.sh start`), `PipelineSyncUiFixture.*` в `o2EditorUITests` (автосохранение, перечитывание, диалоги), `AssetsLineDeleteQuestion.*` (текст вопроса).

## Импорт
`PipelineImport::ParseBytes` читает экспорт AssetsLine по содержимому: JSON пайплайна, JSON-бандл с результатами в data URL (`Parse`) или ZIP-бандл (`ParseZip`: `pipeline.json`, необязательный `manifest.json` со списком `results/<файл>` по нодам с типом и mime - запись с ключом `<nodeId>#<portId>`, называющая оба, это одна часть попортовой ноды - и `uploads` с файлами, которые читают ноды-источники; файлы вне манифеста берутся по имени `results/<nodeId>.<ext>`) в `PipelineGraph` со свежим `id` и карту результатов `PipelineValue`; `StoreResults` записывает их как превью, записи кеша содержимого и отметки актуальности для id пайплайна - сначала загрузки, потому что нода-источник хеширует то, что читает, затем части попортовой ноды под их собственными превью портов и сигнатурами (`PipelineExecutor::PortSignature`); `ImportFile` создаёт ассет в папке, сохраняет результаты под id графа и пересобирает ассеты. `PipelineZip` - небольшой читатель и писатель архивов под этим (записи stored и deflate, zlib).

`O2_PIPELINE_RUN=<файл>` прогоняет ассет `.pipeline` без редактора - тестом `PipelineRunAsset.RunFile` из `o2EditorTests`: выполняются все цели запуска графа с настоящими провайдерами, поэтому арт-пайплайн можно гонять из командной строки вместо окна Pipeline (`O2_PIPELINE_NODE` ограничивает запуск одной нодой, `O2_PIPELINE_ASSETS` задаёт папку, куда пишут финишные ноды, `O2_PIPELINE_WORK` - где лежит кеш, `O2_PIPELINE_TIMEOUT` - бюджет одной цели в секундах).

`O2_PIPELINE_IMPORT=<файл>` заставляет окно Pipeline импортировать этот экспорт AssetsLine на первом обновлении (отладочный ключ, чтобы воспроизводить проблемы импорта без файлового диалога); `PipelineWindow::ImportFile` ловит исключения и показывает их в строке статуса.

`id` графа - ключ кеша, которым пользуется редактор (`PipelineEditor::GetPipelineId`); ассет без id при открытии берёт свой UID, поэтому результаты, закешированные по UID до появления поля, остаются доступны, а граф, сохранённый в другой ассет, сохраняет свой кеш.
