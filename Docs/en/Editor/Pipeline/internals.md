# Pipelines

AI content pipelines: node graphs that turn text, images and sounds into assets through provider APIs and local processing. Sources live in `o2/Editor/Sources/o2Editor/Pipeline` (namespace `Editor`); the editor side is the Pipeline window. The runtime only carries `o2::PipelineAsset`, a `.pipeline` asset holding the graph as a `DataDocument`; `PipelineGraph::LoadFromAsset` / `SaveToAsset` convert between the document and the editor graph. The document is the AssetsLine pipeline JSON (see Format).

> **Three implementations - change them together.** The pipeline editor exists three times: the AssetsLine web editor and server (`AssetsLine/`: `shared/`, `backend/src/`, `frontend/src/nodeEditor/`), this o2 editor (`o2/Editor/Sources/o2Editor/Pipeline/` and `o2/Editor/Sources/o2Editor/Windows/PipelineWindow/`) and the Unity plugin (`AssetsLineUnity/Packages/com.assetsline.pipelines/`). All three read and write the same `.pipeline` document and sync pipelines with each other. A change to pipeline behaviour, a node type, a config key, the file format, the executor and caching rules or the node UI must be made in all three at once, with their tests and docs updated - otherwise synced pipelines diverge.

## Window look

`Windows/PipelineWindow/PipelineTheme.*` holds the two palettes (dark = the AssetsLine tokens, light = the o2 editor colours) under the CSS token names shared with AssetsLine and Unity, the current theme (the editor theme; `SetKind` overrides it for tests and galleries, `FollowEditor` drops that) and a version the editor polls: on a change `PipelineEditor::ApplyTheme` rebuilds the cards and restyles the menus. `PipelineDraw` draws antialiased rounded fills, gradient strokes and Gaussian-like shadows (rings at ±2σ) with a one-pixel fringe in the current target; a checker (picture plates, the composer stage) is one textured rounded mesh with a repeated 2 × 2 texel tile, and the canvas dots, while denser than 32 pixels apart, are one quad with a tile of ten by ten cells rebuilt when the zoom changes - drawn as quads they were hundreds of thousands per frame zoomed out. The controls (`PipelineThemeControls.cpp`: fields, buttons, switches, segments, selects, menus) are built from these drawables, not from the editor's sprite styles; `PipelineRichText` lays Markdown text results out (paragraphs 0.5 em apart, `**strong**` in the semibold face). Card and body metrics follow the AssetsLine constants (`frontend/src/nodeEditor/constants.ts`, `nodeRenderers.tsx`: GAP 7, field 14 + 16.1·lines, actions 27.52, folded list 31.84, fx rows 6 apart). The gated `PipelineThemeGallery` UI test shoots every card of an AssetsLine bundle where the web reference has it on screen, with a block dump (`PipelineLayoutDump`), for pixel and block comparisons.

## Graph

- **Editor::PipelineGraph** — `nodes`, `edges`, saved camera. `Validate()` reports type mismatches and cycles, `WouldMakeCycle(from, to)`, `FindEdgeToPort`, `GetOutgoingEdges`, `RemoveDanglingEdges`, `ResolveSeeds()` (image nodes inherit the seed of the upstream image node when `inheritSeed` is set), `ComputeSignatures()` — a content hash per node built from its config (UI-only keys excluded, see `GetUiOnlyConfigKeys()`), the signatures of upstream nodes and the seed.
- **Editor::PipelineNode** — `id`, `nodeType`, `position`/`size` (y down, as in the web editor), `inputs`/`outputs` (`Editor::PipelinePort`: `id`, `name`, `portType`, `custom`), `config` — a `DataDocument` with `GetConfigString/Number/Bool/Value`, `SetConfig*`, `RemoveConfig`, `HasConfig`. Extra inputs added by the user are kept in `customInputs` (`GetCustomInputs/SetCustomInputs`); `PipelineNodeRegistry::SyncNodeWithSchema` rebuilds the port list from the schema and the custom inputs.
- **Editor::PipelinePortType** — `Text`, `Image`, `Video`, `Audio`, `UiKit`, `TextStyle`; a link connects ports of one type only. `UiKit` and `TextStyle` (names `uiKit` / `textStyle` in the file) are JSON documents stored and synced as text (`IsTextLikePortType`, `PipelineValue::TextOf`, `.txt` cache and preview files); an unknown type still reads as `text`.
- **o2::PipelineAsset** (framework) — the `.pipeline` asset holding the graph document; the editor reads it into a `PipelineGraph` and writes it back on every change.

## Format
A `.pipeline` file is the AssetsLine `Pipeline` document: `schemaVersion`, `id`, `name`, `nodes` (`id`, `type`, `position`, `size` as `{width, height}`, `config`, `inputs`/`outputs` of `{id, name, type, color?, custom?}`), `edges` (`id`, endpoints, `points`), `camera` (`{x, y, scale}`: screen = world * scale + (x, y)). `PipelineGraph::LoadFromJson` / `SaveToJson` (and `LoadFromJsonString` / `ToJsonString`, used by undo and the clipboard too) read and write it; members the editor does not use - `annotations`, `icon`, a port's `color`, anything newer - are kept in `extra` of the graph, node and edge and written back untouched. Whole numbers are written as integers and the rest rounded to 1/1000, so a document read and written without an edit stays byte-stable. The camera converts through a fixed nominal view (`GetNominalViewSize`). The older o2 format (`{"graph": ...}`, reflection) is recognised by `IsLegacyDocument`, read, and saved in the new format on the next save.

Numbers both editors derive from the document agree: the implicit seed is AssetsLine's (32-bit FNV-1a of the node id, `Number()` semantics for `config.seed`, inheritance off only for a literal `false`), and the UI-only config keys are the same list on both sides. A finish node without `assetPath` writes to `Generated/<filename>` (`PipelineNodeRegistry::GetFinishAssetPath`). A paste gives nodes and ports new ids and remaps the ids config refers to (`PipelineNode::RemapConfigPortIds`: custom inputs, composer layers, extract regions).

## Node types

`Editor::PipelineNodeRegistry` holds every `Editor::PipelineNodeSchema` (`type`, `label`, `category`, `description`, `inputs`, `outputs`, `addableInputs`, `instant`, `perPortRun`, `dynamicOutputs`, `defaultSize`) with its implementation (`Editor::PipelineNodeBase::Run` — a `Coroutine<PipelineRunResult>` receiving the execution context and the input values). `AllSchemas()`, `GetSchema(type)`, `CreateNode(type, position)`, `IsFinishType`. Besides `Run` an implementation may override `InitNode(node)` (the config a fresh node starts with), and, for a `perPortRun` node, `SyncPorts(node)` (it owns its output list, so `SyncNodeWithSchema` leaves the schema outputs alone), `PortCacheExcludedKeys()` and `PortCacheVariant(node, portId)` - the config keys the per-port signature drops and what it folds back in for one port.

`Editor::PipelineRegions` is the part list of the extract node: `PipelineExtractRegion` (`id` - the id of the output port carrying it, `name` - what to extract and the port name, a normalised box, `ownTransparency` - whether it carries background settings of its own), `Read`/`Write` on the node config (a node saved before regions existed reads as one part built from its `prompt` and `roi`; `Write` keeps the members a region has besides its id, name and box - its own `transparency`, anything newer - with the region of the same id), `PortNames` (unique, non-empty), `SyncPorts` (rebuilds the outputs keeping the ids, so links survive a rename; a node without a region list keeps exactly one output named `out` - its first port with its links, any other dropped - because AssetsLine looks that output up by the schema name and added a phantom `out` beside a port named after the prompt), `RegionOfPort`, `FindTransparency(node, portId)` (the part's own background settings, null when it follows the node), `SetOwnTransparency(node, portId, own)` (gives the part a complete copy of its effective settings, or drops it), `autoSplitPrompt` and `ParseAutoSplit(answer)` (the model answers with `box_2d` as `[ymin, xmin, ymax, xmax]` on a 0..1000 grid; parts found this way start without settings of their own). A paste remaps region ids in place, so a part keeps its settings through copies.

**Per-part background.** A region may carry `transparency` - the six keys `transparentBg`, `transparentMode`, `chromaColor`, `chromaTolerance`, `chromaSoftness`, `chromaSpill` (`PipelineTransparency::SettingKeys()`), written complete when the part is switched to its own settings. Present, it replaces those node keys for that part; a key missing from a partial object falls back to the node, then to the default (`false`, `twoPass`, `#00b140`, 30 / 15 / 60). Everything that reads them for a run goes through the part's effective settings: `PipelineTransparency::SettingValue(node, portId, key)`, `Read(node, portId)` (the extract prompt, two-pass or chroma), `UsesChromaPostStep(node, portId)`, `ApplyChromaPostStep(node, raw, portId)`, `AnyChromaPostStep(node)` (the editor's auto-apply of the cut sliders), `ImageGenerations(node)` (generations of one run: per part two for a transparent two-pass render, else one - the count AssetsLine multiplies into the price on the play button; the o2 editor shows no price) and the raw-render results of the sync.

**Background rendered by the model.** `PipelineTransparency::SupportsNativeTransparency(model)` answers by the id, trimmed, without a leading `models/`, in any letter case: yes for `gpt-image…` (OpenAI), for `openai/gpt-image-…` except `openai/gpt-image-2` and its dated snapshots `openai/gpt-image-2-YYYY-MM-DD`, for `openai/gpt-5-image`, `openai/gpt-5-image-mini` and `sourceful/riverflow-v2.5-pro`; no for everything else. The id stored in the node decides the mode; a call for a transparent background then takes only the routes whose own id renders it (`RoutesFor(model, true)`), and with no key among them the native provider reports its missing key. For them `Read` gives the effective `mode` `native` whatever `transparentMode` says, and keeps the method of the config in `storedMode`; the config is never rewritten, so `WriteSettings` and the `bg:[...]` part of a port signature use `storedMode`. `UsesNativeTransparency(node, portId)` is true when the background is on (always for `aiRemoveBg`) and the mode is `native`. Such a node or part is not a chroma one: `UsesChromaPostStep` / `AnyChromaPostStep` are false, so the executor keeps no raw render, adds no `chroma-raw` variant and cuts nothing, the cut sliders start no auto-apply, and `ImageGenerations` counts one. The nodes make one call with `transparentBackground` set on `AiRouter::GenerateImage`. `OpenAiProvider` puts `"background": "transparent"` into the `images/generations` body and the fields `background` and `output_format` into the `images/edits` form; `OpenRouterProvider` sends the call to its images API with `background` and `output_format` in the body (`BuildImagesBody`: `model`, `prompt`, `n`, references as `input_references`, no seed and no size); Gemini ignores the flag. The prompts name no backdrop colour (`nativeBackdrop`, `nativeEditSuffix`); `imageExtract` trims the answer by alpha and returns it untrimmed when it has no visible pixel.

Categories: sources (`sourceText`, `sourceImage`, `sourceAudio`), transforms (`textCompose`, `textConcat`, `drawImage`, `imageOutline`, `imageShadow`, `imageGradient`, `imageColor`, `audioProcess`), AI (`aiText`, `textEdit`, `promptGen`, `nanoBananaGen`, `imageEdit`, `imageExtract`, `removeBackground`, `aiRemoveBg`, `aiUpscale`, `videoGen`, `sfxGen`, `ttsSpeech`, `musicGen`), outputs (`composer`, `finishImage`, `finishText`, `finishVideo`, `finishAudio`). `instant` nodes run locally and are re-applied automatically by the editor, from the results their inputs show (`PipelineExecutor::ExecuteSingle`): a node generated again keeps its signature, so a stored result of the effect could be made from the old picture. Cached-only runs still compute sources, which only read their file.

## Execution

`Editor::PipelineExecutor::Execute(pipelineId, graph, targetNodeId, dirtyNodeIds, cachedOnly)` runs the upstream chain of the target in dependency order. Results are cached under `Work/Pipelines/cache/<pipelineId>/{content,previews,ran}` by node signature: a node whose signature matches the cached one is served from disk, `cachedOnly` serves provider nodes from their cache entry or, failing that, from their last rendered preview (without marking them ran), and refuses only nodes that have neither (`Not cached`). `ResolveSourceValue(node, assetsPath, value, error)` (`Nodes/PipelineNodesCommon.h`) is the one place a source node turns its config into a value: the source nodes run through it and the editor uses it to give sources their value without a run. `PipelineUtils::PrettyModelName(id)` maps model ids to the names the model lists show; `PipelineModelMenu` (`Pipeline/PipelineModelMenu.h`) holds the rules of the model menu shared with AssetsLine's `shared/modelMenu.ts` (group of an id, group order and folding, per-field search, Recent, the custom id row), and `PipelineModelPicker` (the Pipeline window) draws it as a popup of `PipelineEditor`; `PipelineOptionPicker` is the same popup without the search for a fixed choice with icons and hints (the prompt writer's target). `PipelineGraph::GetRunTargets()` returns what a whole-graph run targets: every node with no outgoing edges, finish nodes first, skipping sources nothing consumes. A `perPortRun` node is evaluated output by output: only the ports the branch consumes are produced (the target computes all of its own), each under its own signature (the shared config minus `PortCacheExcludedKeys`, plus `PortCacheVariant`) and with its own preview (`GetPortPreviewPath`, `LoadPortPreview`, `NodeOutput` carrying `portId`), so one part failing or changing leaves the others in place; a consumer of such an output hashes the part it reads (`PipelineGraph::ComputePortSignature`, `OutputSigKey`), so two identically configured nodes reading two parts never share a cache slot. The transparency part of a port signature comes from `PipelineTransparency::PortCacheSuffix`: a part without settings of its own hashes byte for byte as before they existed (with the node's chroma cut, its raw render drops `chromaTolerance/Softness/Spill` and is tagged `|chroma-raw`); a part with its own settings drops all six node keys and appends `|bg:[<transparentBg>,"<mode>","<key colour>"]` after the region variant (the key colour stays in the key, as the node's does), then `|chroma-raw` for its raw render, or `|cut:[tol,soft,spill]` for what goes downstream. Its tolerance, softness and spill never enter the raw key, so moving them re-cuts the cached render; switching a part to its own settings changes its key, so it is out of date until it runs again. The executor cuts every part with its own effective settings. `ExecuteSingle` runs one node, `Cancel()` stops after the current node, `assetsPathOverride` redirects finish nodes (tests). Events (`Editor::PipelineExecEvent`): `NodeState` (`queued`, `running`, `done`, `error`; with a `portId` it is about one part of a per-port node - `running` when the part really starts computing, never for a cache hit, then `done` or `error` with the message, all between the node's own `running` and `done`), `NodeOutput` (the `Editor::PipelineValue` with `previewPath`/`srcPreviewPath`), `Retry`, `Log`, `Done`, `Fatal`. `LoadPreview` and `ClearNodeCache` manage the cache from the editor. `PipelineNodeWidget::SetParamsOpen` shows or hides a card's parameter list at once (`paramsOpen`, a UI-only key) and, for a card with a set height, sets `size.y = max(minHeight, shown + autoAfter - autoBefore)`, recorded as a resize; `KeepAreaThrough(change)` does the same for any content change (`PipelineNodeBody::RebuildBodyKeepingArea` for the transparent switch, the method, the model, the extract parts), never snapped to the grid; a resize drag keeps the height at least `GetAutoHeightForWidth` of the width it ends with. The canvas draws the links under the cards, then the cards, then the links leaving a port the body places inside a card (`PipelineNodeWidget::IsBodyPort`, the parts of an extract node) with the same colours and selection, then the port markers; picking a link does not depend on the order. The editor keeps the part states in `PipelineNodeRuntime::portStates` and drops them once the node stops running or queued; `PipelineNodeWidget::ApplyRuntime` hands every state change to the body (`PipelineNodeBody::OnRunStateChanged`), and the extract card updates its cells in place.

Finish nodes write the result to `<assets>/<assetPath>.<ext>` (optionally cropped and resized; `keepAspect` fits the image into `resizeW`x`resizeH` instead of squashing it) and set `assetsChanged`; in the editor the executor then calls `o2Assets.RebuildAssets()`, or, with `deferAssetsRebuild` (the Pipeline window), reports it in `Done` and leaves the rebuild to the window (see Background work and status).

`Editor::PipelineValue` — `type`, `data` (text or encoded bytes), `mimeType`; `Text`, `Image(bitmap)`, `ImageBytes`, `Bytes` constructors, `GetBitmap()`; `DecodeImageBytes` decodes PNG/JPEG bytes. `Editor::PipelineUtils` — work paths (`SetWorkPathOverride`), uploads, data URLs, base64, FNV hashing, hex colours, file bytes.

`PipelinePairLayout` (`Pipeline/PipelinePairLayout.h`) holds the input | result rules shared with AssetsLine's `extractPair` / `cellCorner`: which node types show their input beside the result (`IsPairNode`, `InputPortOf`), pane width and row height, the extract grid (`ExtractGrid(rowWidth, parts, rowHeight)`: the natural row fits columns no narrower than 64 and is never lower than 176, a hand-sized card makes it taller; in the row one part fills the pane, several are square cells in the column count that makes them largest, the grid centred (`offX`, `offY`), captions of 20 under the cells; `ExtractCellCorner` gives the port position, the top-right corner of a cell's image; the cell's regenerate / remove buttons stand at the top left and the corner is cut out of the cell's click area), height 0 as "automatic" (`IsAutoHeight`, `NewNodeSize`, `HeightAfterResize`), `ShowsCompare`, the local view setting (`GetIoView/SetIoView`, `Work/Pipelines/ViewPrefs.json`, a version the open editors watch to rebuild the pair cards) and the per-node divider. In the window, `PipelineNodeBody::AddPairRow` adds a `PipelineIoPair` (input pane, result widget, `PipelineCompareView`); the image edit and extract bodies put the result or the parts grid beside the drawing stage (`PipelinePaintEditor::SetBeside`, `SetCompare` for the split stage), and the extract body places each part port with `GetRowPlacement` + `ExtractCellCorner` (`HasBodyPort`, `GetBodyPortOffset`). `PipelinePairDraw` draws the clipped images, the one screen pixel divider and the screen-sized grip (`BadgeScale` = min(pixel size, 1.5), `GripRect`).

A body can carry the input ports itself: `PipelineNodeBody::InputsInBody` takes them out of the port rows (with the add-input row), `GetBodyPortOffset` places each at the card's left edge and `IsAddInputAt` is the body's add-input row; the composer does this with `PipelineComposerLayersPanel` (`PipelineComposerLayers.h`), whose pinned row heights give the port positions without measuring; `GetAddInputPlace` tells which add row a point is on. `PipelineComposerLayout` (`Pipeline/PipelineComposerLayout.h`) holds the composer rules shared with AssetsLine's `shared/composer.ts` / `composerLayout.ts`: the rows of the list (`Rows`: `+ layer on top`, the layer rows with the open settings, `+ layer below`), the export size of a layer (`LayerExportSize`, `HasExportSize`, `TypeExportSide`; `exportW` / `exportH` in `config.layers[id]`, kept through a read and write of the layer), where a new layer lands (`OrderWithNewLayer`, `PlaceNewLayer`: `layerOrder` and `selectedLayer`, written by `PipelineEditor::AddCustomInput` and by a link dropped on an add row in the undo step of the input and the link) and `FrameScale` = clamp(1 / camera zoom, 0.5, 4), by which `PipelineComposerFrame` (the engine's `FrameHandles` with screen-sized handles) and the size badge are sized.

`PipelineUpscale` (`Pipeline/PipelineUpscale.h`) holds the AI upscale rules of AssetsLine's `shared/upscale.ts`: `Target` (×2/×3/×4 or the size with the aspect lock, capped at 8192), `ClosestAspect` among the frames a model renders, `RenderSizeFor` (1K / 2K / 4K), `RendersLargeSizes` (the Gemini 3 image models, direct or through OpenRouter) and the prompt. An image call takes `AiImageOptions` (render size and frame): Gemini puts them into `generationConfig.imageConfig` (`GeminiProvider::BuildImageBody`), OpenRouter's chat body into `image_config`, OpenAI picks the nearest of its three sizes (`OpenAiProvider::SizeFor`).

`PipelineEditRegion` (`Pipeline/PipelineEditRegion.h`) is the edit region of the image edit node, the same rules as AssetsLine's `editRegionOf` / `regionBoxes` / `pasteRegionEdit`: `Read` validates an `editRegion` value, `Of(node)` reads it from an image edit node, `PixelBoxes` gives the region in pixels and the context box, `Weight` the blend weight of a box pixel and `PasteRegionEdit` blends the model's answer back. `PipelineTransparency::Read` reports no transparency for an image edit node with a region, so the chroma post-step, the native request and `ImageGenerations` follow. In the window, `PipelinePaintEditor::Init(node, withRegion, regionKey, optionalRegion)` keeps the box under a key: `roi` for the extract source, the optional `editRegion` for the image edit stage, created by the region tool and cleared by its remove tab; `SetDrawingEnabled(false)` (the extract) drops the tool row and the drawn layer and keeps the boxes editable, and the extract mirrors the selected part's box into `roi` when a pipeline saved elsewhere left it out of step. `AiRouter::SetImageStub` sends every image request to a function instead of a provider (tests).

Every entry point that can build card widgets between frames (`PipelineEditor::Update`, `OnExecutorEvent`, `PipelineNodeWidget::OnOutputChanged/OnConfigChanged/ApplyRuntime`, `PipelineNodeBody::RebuildBody`, the composer's layer panel) pushes `PushEditorScopeOnStack`: a widget built outside the editor scope is registered as a scene object, which polluted the scene and crashed it when the card was rebuilt.

Executor events reach the editor on the main thread: the executor's coroutines resume on the job workers (`co_await` starts a child on `JobThread::Any`), so `PipelineEditor`'s `onEvent` hands every event to a main-thread job (a copy without the decoded bitmap cache, since `o2::Ref` counts are not atomic) and `OnExecutorEvent` runs there.

## Background work and status

The window keeps the main thread to the UI; what costs time runs on the job workers or is spread over frames, and is shown while it runs.

- **Pictures.** An image value keeps its decoded picture in a slot shared by its copies (`PipelineValue::decoded`, `ShareDecoded`, `PeekBitmap`); the editor gives every value it stores a slot (`LoadPreview`, `OnExecutorEvent`, `RefreshSourceOutput`), so a picture is decoded once however many cards show it. The cards ask through `PipelineNodeBody::Picture` → `PipelineEditor::GetPicture`: a picture not decoded yet is decoded by `PipelineImageLoader` on a worker together with its copy of at most 1024 px, the card shows `loading..` meanwhile, and `ApplyDecodedPictures` hands the results over between frames within 6 ms, calling `OnOutputChanged` of the cards that asked. `PipelineDisplayCache` keeps one card-sized texture per bitmap for every view (image views, pair and compare views, the paint stage, the composer layers). Source images are read without a decode for the cards (`ResolveSourceValue(..., decodeImage = false)`). A paint canvas (image edit, paint) whose picture is still decoding is not laid out meanwhile (`PipelinePaintEditor::SetBackground(bitmap, pending)`): the stored drawing is loaded once, at the picture's size. Audio and video cards share one `SoundAsset` per clip, since an asset stays in the assets cache for the session.
- **Runs.** `ExecuteWork` / `ExecuteSingleWork` (the inputs, the node, its previews, its cache entry, the signatures) run on a worker; only `FinishRun` comes back to the main thread. The editor sets `deferAssetsRebuild`: a run's `Done` carries `assetsChanged`, and the assets are rebuilt once, after the last queued run, in the background (`Assets::RebuildAssetsInBackground`); saving the asset (`IAssetEditorWindow::SaveEditingAsset`) and saving composer layers rebuild the same way. Video previews read their frame atlas on their own thread.
- **Cards.** Undo, redo, a reload, deleting and pasting change the cards they concern only (`SyncGraphTo`, `AddCard`, `RemoveCard`); a composer layer renamed or an extract part renamed keeps the card and its rows. Cards out of view are laid out a few a frame after opening (`WarmUpCards`, 2 ms a frame). A moved camera is written into the asset document 0.25 s after it rests. The links of a frame are collected once for both passes (`CollectEdgeDraws`).
- **Status.** `PipelineEditor::GetBackgroundStatus()` (`Loading previews 12/150`, `Applying Outline`, `Rebuilding assets`) is shown in the window toolbar; a card busy in the background (`PipelineNodeWidget::IsBusyInBackground`: its effect applying, its pictures decoding) draws a thin running bar under its header.

`PipelinePerfUiFixture.*` in `o2EditorUITests` times the main actions on the big pipelines of the project (`O2_PIPELINE_PERF=1` or the project folder, results as JSON to `O2_PIPELINE_PERF_OUT`); `PipelineResponsivenessUiFixture.*` keeps the behaviour above.

## Second step: the checks against the reference

**The refine step.** A node may have a paid second step over a port's stored generation: `IPipelineNodeImpl::RefineKey(node, portId)` (empty while the step is off), `Refine(ctx, inputs, node, stored, key)` -> `PipelineRefineResult {value, keep}` and `RefineReplayed(ctx, node, key)`. `PipelineExecutor::RefineStored` (`PipelineExecutorRefine.cpp`) runs it after the generation is stored or read back - for every part of a per-port node and for a single-output node (a picture, or a text style: its JSON counts as its bytes; other text is never refined) - and before the chroma cut, `PostStep` and the crop. Its result is cached under `RefineSignature(cacheSig, key, stored)` = the first 32 hex digits of sha256(`<cacheSig>|<key>|` + the generation's bytes), so a restored or regenerated generation is checked anew; `keep: false` (a model call failed) stores nothing and the next run tries again; ↻ deletes it with the generation. A cache hit logs `check cache hit` and calls `RefineReplayed` (the debug file follows the stored check). A cached-only run never pays for it: where it has not run the stored generation stands as it is, the log says `check not run yet`, and the node is not marked as run (`refineOwed`). The context carries the part (`outputPortId` / `outputPort`), `workDir`, `fresh`, the memo (`PipelineExecutor::AttachWork`, shared with dynamic outputs nodes; `ctx->MemoGet` / `MemoPut`) and `phase`: `ctx->Phase("check" | "redo")` emits `NodeState running` with `PipelineExecEvent::phase` for the part (or the node), kept by the editor in `PipelineNodeRuntime::phases` until the part stops. o2 keeps no takes, so the web's "kept attempt as a take" has no counterpart.

**AI extract: check against the reference** (`PipelineExtractCheck`, `PipelineExtractCheck.cpp` + `PipelineExtractCheckRun.cpp`, port of `backend/src/nodes/extractCheck.ts`). Config `refCheck` (off), `refCheckMax` 1/2/3 (2), `refCheckModel` (`gpt-6.1-sol`): `PipelineExtractCheck::Read`; refine key `ref-check:v1:<model>:<limit>`. The keys stay out of a part's generation key and, while off, out of the node signature (`PipelineGraph::IsRefCheckOn`). Per attempt: the sprite of the stored generation (`SpriteViewOf`: a chroma part is cut as the post-step cuts it, any other part is stored trimmed with its frame in the tEXt `AssetsLine:frame` = `frameW,frameH,left,top`, written by `PipelineExtract::GeneratePart` only while the check is on, `ReadPngFrame`; without it the sprite is centred), laid on its crop (`PlaceOnCrop`: the measured size from `PipelinePartFit`, a coarse shift, then `UiLayout::Register`), over the reference = the region with a quarter of its side around it (`RegionRect`, `ContextRect`, `OverlayOn`: pixel difference and changed share), the judge gets reference, overlay and the sprite on a checker (`SpriteOnChecker`) scaled to 384..1024 px with `JudgePrompt`, answers `{verdict, likeness, differences, instructions}` (`ParseJudge`); `significant` regenerates the part with `ClarificationsOf` added to its prompt (`GeneratePart(..., extra)`), up to the limit; `BestAttempt` keeps accepted attempts first, then the likeness. Judge and draw answers are memoised (`ShaKey`: `extract-check-judge:v1` / `extract-check-draw:v1` + what was asked); an opaque part or a plate is skipped. Debug data: `<work>/check/<part>.json` (and `<part>-<key8>.json`, the reference, sprite and overlay pictures; `running: true` while it goes; the last three checks of a part are kept, parts that are gone are pruned).

**AI text style: check against the picture** (`UiDoc/UiStyleCheck.*`, port of `backend/src/uiKit/styleCheck.ts`): the same three keys, refine key `style-check:v2:<model>:<limit>` (bump it when the judge's prompt changes). The words of the lettering are drawn in the style by the layout renderer on the picture's own border colour (`StyleBackdropOf`; the grey matte for a transparent picture) at most 1024 px wide (`RenderStyleSample`, `SampleDoc`), the judge gets the picture as the style model saw it (`StyleSourcePicture` with `srcCrop`) and the sample with `StyleJudgePrompt` (the style it may change, the earlier attempts, the font catalogue, `StyleLookSpec`); its `style` fields are laid over the attempt (`ApplyJudgeFix`: never size, name or role), `StyleChanges` lists what changed, the best attempt by likeness is kept with the name, role and `extracted` of the reading. Debug data: `<work>/check/style.json`.

**Cards.** `PipelineCheckRows::Add` puts a divider, the switch and, while it is on, the limit segments and the judge model row into a parameter list; `PipelineCheckDlg` is the details window (attempts side by side, the stop line, a 1:1 zoom; it follows the debug file while it changes). The AI extract card adds a third button to the part's tool strip and shows the part's phase under its spinner; the AI text style card is `PipelineTextStyleExtractBody.cpp` (source crop editor on `srcCrop`, the sample, the summary chips, the hint, `→ Text style` through `PipelineEditor::AddNodeBeside`, the folded parameters).

Tests: `PipelineExtractCheck.*` (14, the web's `extractCheck.test.ts` with the image and vision models stubbed), `PipelineStyleCheck.*` (the check part of `textStyleFx.test.ts`, the backdrop, the fix, the cached-only and ↻ paths) in `o2EditorTests`; `PipelineChecksFixture` in `o2EditorUITests`.

## AI image to UI

Retired since 2026-11-12 (`schema.retired`): the AI UI layout does this with a UI kit; nodes already in pipelines load and run.

`imageToUi` (`Pipeline/Nodes/ImageToUiNode.*`, the core in `Pipeline/UiLayout/`, namespace `Editor::UiLayout`) works like [XuToWei/Image-To-UI](https://github.com/XuToWei/Image-To-UI): its skill runs **unchanged** (Python), with the vision model as the agent the skill was written for. The node makes what the skill takes as given - a folder of sliced sprites, cut from the mockup - answers the agent's model calls and turns the skill's task folder into the outputs. It is the port of AssetsLine's `backend/src/uiLayout/run.ts`, the host contract is `o2/Tools/ImageToUi/PORTING.md`. `PipelineImageToUi` (`Pipeline/PipelineImageToUi.h`) holds what the three editors agree on (AssetsLine's `shared/imageToUi.ts`): the defaults, `ReadConfig` (`maxTurns` 4..120, the card offers `TurnOptions` 20 / 40 / 60 / 90 / 120, default 60), `SpriteName` (`preview` / `layout` become `sprite_<key>`), `SpritePorts`, `SummarizeLayout` (sprites = the distinct `asset`s), `ReadRunSummary` (the trace's `summary`), `RunLine`, `SummaryLine`, and the rules of the edits after a run (below).

**Outputs decided by the run.** A schema with `dynamicOutputs` is run once for all its outputs (`PipelineRunResult::outputs` by name, `order` the run's order) in `PipelineExecutor::EvaluateDynamic` (`PipelineExecutorDynamic.cpp`). The result is a bundle under the node signature: `content/<sig>-outputs.json` = `{"outputs":[{name,type,key,ext}]}` and a file per output under `BundleKey(sig, name)` = the first 32 hex digits of sha256(`<sig>#<name>`); a load missing any file is a miss, one computation runs per pipeline and signature at a time, a bypass (↻) deletes the bundle and sets `ctx->fresh`, `cachedOnly` reports `Not cached`. `DynamicPorts` gives the ports: the schema outputs first, then the rest in run order; an output the node already has keeps its port id, a new one gets the schema id or `sp-<name>` (characters outside `[A-Za-z0-9_-]` as `_`). The executor emits `NodePorts`; `PipelineEditor::ApplyNodePorts` gives the live node those outputs, drops the links of ports that went, rebuilds the card and saves the pipeline with no undo step. The first output is the node's preview, every other one a port preview (images `.png`, the layout `.txt`), stale port previews are deleted. The context carries `workDir` (`Work/Pipelines/cache/<pipeline>/work/<node>/`, the trace), `fresh` and `memoGet` / `memoPut` (model answers memoised in the content folder under `uil-t-` / `uil-i-` keys: the first 40 hex digits of sha256 over the NUL-terminated parts). A consumer's cache key of a dynamic output is `PipelineGraph::DynamicPortSignature(sig, port)`, so two outputs never share a slot. Sync sends outputs 1..n as parts `<node>#<port>` with the extension of the port type, and seeds a downloaded result as a bundle (`AssetsLineSyncResults::SeedBundle`), so a run made on the web exports here without asking the models again.

**The Python** lives in `o2/Tools/ImageToUi/`: `upstream/` (the skill, never edited), `agent/agent.py` (the agent's environment) and `PORTING.md`, copied from `AssetsLine/image-to-ui/` by `tools/sync-image-to-ui.sh` (o2-Template). `ImageToUiHome` finds it from the project root or upwards from the working folder (`O2_IMAGE_TO_UI_DIR` overrides). The interpreter is the pipeline setting `imageToUiPython` (`Python 3` in the AssetsLine dialog); empty, `FindPython` takes the first of `python3` on `PATH`, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` that imports Pillow and numpy (the probe is cached per `PATH`), else the first found - the agent then exits with code 3 and its `detail` (what to install) is the node's error.

**The run** (`UiLayoutRun.cpp`): analysis (`Prompts::Analyze`, `ParseAnalysis`: ids, grids expanded into cells with their texts; `AnalysisFrameOf(model, w, h)`: a Gemini model answers `box_2d` on 0..1000, any other gets the design scaled to at most 1568 px / 1.15 MP and answers `box` in pixels of that picture, mapped back by `BoxFromPixels` - other models drift on the 0..1000 grid; then `FitGrids` (`UiLayoutGridFit`) moves every grid onto the cells the picture shows: the pitch is the period of its edges, the cell borders run through its gutters, an empty column or row the model added is dropped, a box a row short takes the picture's pitch, kept only when its lines are quieter than the model's; the step notes what moved and keeps the boxes as answered beside the fitted ones), the texts measured by their ink (`UiLayoutMeasure`; only for what a cut must erase), `PlanLooks` and the cuts (`CutAll`, four at a time, each worker with its own `ParallelAiCtx`; `UiLayoutSlice`, `UiLayoutMatte`: crop, key colour, model render, chroma key, registration, warp, despill, composite, leftover fill, nine-slice margins for panels; a bad matte is cut again with another seed), the backdrop (`MakeBackground`: a colour, or a plate checked by `PlateLeftovers`, asked once more and filled by `HarmonicFill`). Then the skill's inputs in `<workDir>`: `input/design.png` (flattened on white) with the three Roboto files beside it, `sprites/<name>.png` flat (`AssetFileName`: the look key made safe plus `panel_` / `button_` / `bar_` / `icon_` unless the key says it; duplicates `_2`), `<name>.png.meta` with the Unity `spriteBorder` for nine-sliced looks (`NineSliceMeta`), `sprites/bg_backdrop.png` for a plate, `fonts/Roboto-*.ttf` + `LICENSE-Roboto.txt`, a fresh `task/` and `agent-view/` (the kept states of earlier rounds - `rounds/`, `edits/`, `rounds.json` - go too). The trace is flushed, the agent runs, the trace is reloaded (the agent appended its steps), and the outputs are `task/reconstruction.png` (`preview`), `task/ui_structure.json` byte for byte (`layout`) and one image per sprite the layout names (`AssetRefs`: every `asset`, states included), in the order the layout first uses them (a name without a file in `sprites/` is skipped; nine-slice borders from its `.png.meta`). A result with `ok: false` fails the node (`the agent ended without a checked layout (<error or status>)`); a run that is not complete still delivers its outputs, the log and the trace say NOT completed with the blockers. The steps go to `<workDir>/trace/trace.json` with their pictures as they happen (`Trace`).

**Edits after a run** (`UiLayoutRounds.cpp`, the port of `run.ts` `runLocked` / `Rounds`; host contract: `PORTING.md` section 6). ## AssetsLine sync
`Editor::AssetsLineSync` (`o2/Editor/Sources/o2Editor/Pipeline/Sync`) keeps the pipeline assets of one folder and a linked AssetsLine project in step; `EditorApplication` owns it and calls `Update` every frame, the Pipeline window gives it `isPipelineFileBusy` (the edited asset has unsaved changes), `onPipelineFileChanged` (reload the edited asset), `onResultsChanged` (reload previews) and `confirmDeletes` (the question `AssetsLineDeleteDlg`), and autosaves a synced pipeline a second after an edit. The link is `o2::AssetsLineConfig` in `o2Config.assetsLine` (`enabled`, `serverUrl`, `projectId`, `projectName`, `folder`, `writeFinishAssets`, `pollInterval`); the token and the sync state are per user in `Work/Pipelines/sync/` (`credentials.json`, `state.json`, `base/<id>.json`).

`AssetsLineClient` sends the requests (`Authorization: Bearer`, `X-Project-Id`, `X-Sync-Client`) through `o2Network`. Connecting: `StartConnect` asks the server for a code and opens its approval page, then polls until the token comes; `ConnectWithToken` checks a hand-made token with `/api/sync/me`.

A pass (`SyncPass`, coroutine) reads `/api/sync/state`, then:
- **documents** (`SyncDocuments`): scans the folder (a file without an id adopts its meta UID, a copied file gets new ids, an asset-backed source gets an upload id from its content), compares every pipeline with its base (the last version both sides had, camera ignored) and the stored revision: pushes a local change with `baseRev` (the server merges it with changes made meanwhile when the base comes along; a merged answer is written back unless the file changed again), pulls a remote change, renames and deletes on either side; files the editor holds unsaved are skipped. A pipeline whose file is gone here while the server still has the base revision is deleted there unasked only when it is the one such pipeline of a pass that is not the link's first (`RestartLink`: state load, connect, disconnect, sync off or not connected, a change of server, project, assets path or folder; the first pass ends with a document exchange that did not go offline); otherwise `confirmDeletes` asks (no hook - pulled back in the same pass). Asked ids are skipped entirely until the answer; the answer is used by the next pass that reaches the id, applied only if the file is still gone and the server rev unchanged, and put back when the action fails;
- **results** (`SyncResults`, when the server's result counter or a local file moved): maps AssetsLine result keys (`<node>`, `<node>.src`, `<node>#<port>`, `<node>.raw` / `<node>#<port>.raw` for the raw render of a chroma node or of a part whose effective settings are chroma, `<node>.trace` for the debug steps of AI image to UI - its `trace/` folder as one zip (`ZipTrace` / `UnzipTrace`, versioned by `trace.json`, replaced whole), sent only for a node fresh here, handled before the other keys and never holding a node back - a server that refuses it is not asked again until the next run) to the preview and content files of `Work/Pipelines/cache/<id>/`, uploads what changed here and downloads what changed there (both changed: the fresh one wins), exchanges source uploads, marks fresh on the other side what is fresh on this one - a node fresh on the server gets its download copied into the content cache under the key a local run looks it up by (`PipelineExecutor::ContentSignature`); a node generated again on either side keeps its signature, so a result that arrives replaces the kept generation, and a result sent from here is marked fresh again for the server to do the same - and writes finish results into the assets (downloaded, or computed by a cached-only run of the finish node).

Tests: `PipelineFormat.*` (format, seeds, round trip of the AssetsLine documents found on the machine), `AssetsLineSync_.*` (end to end against a real server: set `O2_ASSETSLINE_TEST_URL`, a throwaway one is started by `AssetsLine/backend/scripts/test-instance.sh start`), `PipelineSyncUiFixture.*` in `o2EditorUITests` (autosave, reload, the dialogs), `AssetsLineDeleteQuestion.*` (the question text).

## Import
`PipelineImport::ParseBytes` reads an AssetsLine export by content: a pipeline JSON, a JSON bundle with data URL results (`Parse`) or a ZIP bundle (`ParseZip`: `pipeline.json`, an optional `manifest.json` listing `results/<file>` per node with its media type and mime, files not in the manifest keyed by `results/<nodeId>.<ext>`) into a `PipelineGraph` with a fresh `id` and a map of `PipelineValue` results; `StoreResults` writes them as previews, content cache entries and freshness markers of a pipeline id; `ImportFile` creates the asset under a folder, stores the results under the graph id and rebuilds the assets. `PipelineZip` is the small archive reader and writer behind it (stored and deflate entries, zlib).

`O2_PIPELINE_RUN=<file>` runs a `.pipeline` file headlessly through the `PipelineRunAsset.RunFile` test of `o2EditorTests`: every run target of the graph is executed against the real providers, so an art pipeline can be driven from the command line instead of the Pipeline window (`O2_PIPELINE_NODE` limits the run to one node, `O2_PIPELINE_ASSETS` says where finish nodes write, `O2_PIPELINE_WORK` where the cache lives, `O2_PIPELINE_TIMEOUT` the seconds budget of one target).

`O2_PIPELINE_IMPORT=<file>` makes the Pipeline window import that AssetsLine export on its first update (a development aid for reproducing import problems without the file dialog); `PipelineWindow::ImportFile` catches exceptions and reports them in the status line.

The graph `id` is the cache key the editor uses (`PipelineEditor::GetPipelineId`); an asset without one adopts its UID on open, so results cached by UID before the field existed stay reachable, and a graph saved into another asset keeps its cache.
